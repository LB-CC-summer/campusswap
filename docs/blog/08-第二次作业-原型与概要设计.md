### 1.4 交互与规则要点

| 机制 | 界面表现 | 规则 |
|---|---|---|
| 筛选与硬条件 | 集市页三项筛选、结果页条件标签 | 校区为硬过滤，不由模型放宽；无命中时给出重置筛选、切换校区、保存求购三个出口 |
| 敏感信息打码 | 聊天页号码为 `138****5678` | 消息写入即打码，不保存原文，打码后不可还原 |
| 联系方式交换 | 「申请交换联系方式」→ 填写表单 → 对方同意 → 显示号码 | 号码由申请人主动填写并加密存储；同意与关闭是两个独立动作，各有记录 |
| 草稿与发布 | 智能发布结果页为草稿态，确认后才进集市 | AI 生成内容落库为 `status='draft'`，用户确认后转 `on_sale`；缺项由模型追问，不代为编造 |
| 禁用与失败态 | 按钮置灰并给出原因文案 | 商品非在售时购买按钮禁用；并发失败方收到 409「手慢了，该商品已被预订」 |
| 后台授权留痕 | 举报详情页的授权按钮 | 查看聊天按次授权、24 小时失效；审计日志只追加，不可改删 |

原型走查按 20 帧逐页执行，产出《原型走查记录》，记录每帧跳转目标、按钮禁用条件与异常文案，共闭环 12 个问题。其中一处为原型与接口契约不一致（首页展示已预订商品，接口仅返回在售），最终以接口返回"在售 + 已预订并置灰"解决。

## 二、概要设计

### 2.1 系统架构与功能模块

功能模块自顶向下拆为两层（图 3-1）：左侧前端 11 个页面，右侧后端 11 个模块（auth、users、campus、products、category、search、chat、privacy、trades、agent、admin），下一层为数据与依赖（MySQL 8.0、对象存储、大模型 API）。页面与模块一一对应，例如「智能找物」对应 `search` + `agent`，「消息中心」对应 `chat` + `privacy`。

![图 3-1 功能模块结构](https://cdn.jsdelivr.net/gh/LB-CC-summer/campusswap@v1.0-docs/docs/uml/11-module-map.png)

**图 3-1　功能模块结构（前端 11 页面 / 后端 11 模块 / 数据与依赖）**

系统分五层：表现层、接入层、业务服务层、智能体层、数据层（图 2-2）。其中一条约束被明确画出并落实到代码：**智能体层不直连数据库，只调用业务服务层接口**。

![图 2-2 分层体系结构](https://cdn.jsdelivr.net/gh/LB-CC-summer/campusswap@v1.0-docs/docs/uml/00-architecture.png)

**图 2-2　系统分层体系结构**

这样约束的原因是两个入口必须共用同一份业务规则：AC-03 要求自然语言找物返回在售商品，AC-06 要求推荐卡片的字段与商品详情一致。若智能体自行查库，过滤规则、状态范围与权限校验会分叉，出现"页面搜不到、AI 搜得到"。技术选型为前端 Vue 3 + TypeScript + Vite + Element Plus，后端 Python 3.10 + FastAPI，数据库 MySQL 8.0，消息用 WebSocket，图片走对象存储。

### 2.3 数据库设计

16 张表分四组：基础配置（`campus`、`category`）、用户与身份（`user`、`user_profile`）、商品与检索（`product`、`product_image`、`favorite`）、交互与交易（`conversation`、`message`、`contact_exchange`、`block`、`trade`、`report`、`chat_access_grant`、`admin_audit_log`、`agent_session`）。

概念模型为 14 个核心实体（含智能体会话 `agent_session`），物理表 16 张；多出的 `chat_access_grant`（按次授权）与 `admin_audit_log`（后台审计）是两张支撑表，为需求"按次授权、全程留痕"的直接产物。

**图 5-2　E-R 图（16 张表）**


对象关系映射（实体类 ↔ 表）：

| 实体类 | 表 | 主键 | 说明 |
|---|---|---|---|
| `User` | `user` | `id` | 登录凭证与角色，邮箱以哈希存储 |
| `UserProfile` | `user_profile` | `user_id` | 昵称、头像、校区，与认证信息分离 |
| `Campus` | `campus` | `id` | 含 `is_cross_city`，决定跨市邮寄校验是否启用 |
| `Category` | `category` | `id` | 类目属性模板以 JSON 存储 |
| `Product` | `product` | `id` | 状态五态，价格定点小数 |
| `ProductImage` | `product_image` | `id` | `sort_no = 0` 为主图 |
| `Favorite` | `favorite` | `(user_id, product_id)` | 联合唯一 |
| `Conversation` | `conversation` | `id` | 由商品 + 买卖双方唯一确定 |
| `Message` | `message` | `id` | 内容写入即打码，无原文 |
| `ContactExchange` | `contact_exchange` | `id` | 号码加密存储，三态 |
| `Block` | `block` | `(blocker_id, blocked_id)` | 联合唯一 |
| `Trade` | `trade` | `id` | 含生成列 + 唯一索引 |
| `Report` | `report` | `id` | 举报是管理员查看聊天的唯一入口 |
| `ChatAccessGrant` | `chat_access_grant` | `id` | 按次授权，24 小时失效 |
| `AdminAuditLog` | `admin_audit_log` | `id` | 只追加，无删除接口 |
| `AgentSession` | `agent_session` | `id` | 存已确认条件，支撑多轮增量 |

并发唯一性由数据库约束保证，不由应用层"先查后改"保证：

```sql
confirmed_product_id BIGINT UNSIGNED
  GENERATED ALWAYS AS (IF(status = 'confirmed', product_id, NULL)) STORED,
UNIQUE KEY uk_confirmed_product (confirmed_product_id)
```

同一商品只能存在一条 `confirmed` 交易，第二次插入直接撞唯一键，应用层捕获 1062 返回 409。不采用 `UNIQUE (product_id, status)` 的原因：该约束挡不住多条"已取消"，且会阻止"取消后重新上架再成交"；生成列仅在 `confirmed` 时取值，取消后转为 NULL，不参与唯一性判断。

### 2.4 关键设计决策

说明书 2.6 节记录十条决策，每条写明理由、代价与关联验收标准。以下三条代价最明确：

| 决策 | 选择 | 代价 |
|---|---|---|
| D-05 | 交易先到先得，不设卖家二次确认 | 卖家无法挑选买家，可能被恶意下单锁货 |
| D-06 | 聊天敏感信息写入即打码，不保存原文 | 打码不可逆，举报时无法还原原文作为证据 |
| D-10 | 大模型失败时降级为关键词 + 硬条件检索 | 推荐解释质量下降，界面须明示"已降级" |

另有两处与需求文档的差异已在说明书附录 A 记录并说明理由：草稿落库（`status='draft'`）而非仅存前端，以及联系方式改为用户主动填写、单表存储（`contact_exchange`），以同时满足"原文不落库"与"同意后可见"。

协作方式有两条硬约定。其一，代码与文档统一走分支流程：`feat/部分` → `develop` → `main`，合并前须一人 review，`main` 始终保持可演示状态。其二，每位成员至少有一次本人的提交记录，代提交视为未参与——助教按人核查贡献，7 人的提交记录均可在仓库 Commits 中按作者核对。

文档以 Markdown 入库，PDF 由仓库内 `tools/` 脚本生成（Markdown → DOCX → PDF），任何人拉取后均可重新构建，不依赖个人电脑环境。任务分派见 `docs/pm/第二次团队作业-任务分派清单.md`，按人待办见 `docs/pm/待办-按人.md`。
