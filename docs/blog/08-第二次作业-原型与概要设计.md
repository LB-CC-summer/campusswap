## 一、写在前面：这一周我们推翻了九处自己写过的决定

设计阶段最难的不是画图，是发现需求文档里那些"当时觉得没问题"的话，其实落不了地。这一周我们把需求文档翻烂了，设计阶段一共改掉九处，全部记在《系统设计说明书》附录 A 的设计变更说明里，每条都写了"为什么改、代价是什么"。挑三条说，因为它们直接改变了产品长什么样。

**第一条：交易从"卖家挑买家"改成"先到先得"。**

需求文档里写的是买家提交申请、卖家从中确认一单。看起来更符合二手交易"卖家挑人"的真实感受。但真正落地时发现两件事：一是这个流程要多一个接口、多一个页面状态、多一套通知，七个人的时间撑不住；二是"先查后改"的并发控制在应用层写，只要两个请求在查询和更新之间插进来，就会卖出两次，而验证这个漏洞需要写并发测试，我们未必写得对。

改成先到先得之后，买家点"立即购买"就是一条 `INSERT`，数据库对"已确认交易的关联商品"建唯一索引，第二条插入必然撞唯一键冲突，捕获后返回"商品已被预订"。**并发正确性不再由我们的代码保证，而由数据库的原子约束保证。** 代价是卖家不能挑人，遇到恶意下单只能事后取消——我们接受这个代价，因为一个能演示、不会卖重的东西，比一个功能完整但可能出错的东西重要。

**第二条：智能体不再用可视化平台编排。**

第一次作业里我们选了扣子（Coze）做流程编排，理由是调试直观、答辩能直接展示编排图。设计时发现这个选择的真实成本：编排配置和提示词放在第三方平台上，进不了 Git，改了什么、谁改的、能不能回滚，全都没有记录。评审老师问"你这版提示词和上版的差异"，我们答不出来。改成自建工具层、直连大模型 API 之后，提示词和工具定义都在自己的仓库里，可以 diff、可以回滚。

顺带说清楚一件事：**两种方案下业务数据都不出库**。工具跑在我们自己的 FastAPI 里，模型只负责理解意图和选择调用哪个工具。所以这次变更不涉及数据边界，只涉及工程可维护性。

**第三条：聊天里的手机号，打码之后就真的不存在了。**

需求文档写"双方同意后显示完整号码"，读起来天经地义。但配上"聊天原文不落库"这条隐私设计，就变成一个死结：原文都没存，同意之后从哪里读号码？

我们的解法是把"交换联系方式"从**被动抓取聊天记录**改成**用户主动填写**：想交换的一方在独立表单里填写号码，加密存入 `contact_exchange` 表，对方同意后按会话解密返回。这样"原文不落库"和"同意后可见"同时成立，隐私性也比偷偷识别聊天记录更强——平台从来没有、也不需要知道你聊了什么。

这三条改完，产品语义其实动了。所以我们把 18 条验收标准逐条对照了一遍，其中 AC-10、AC-15 的措辞需要同步修订，这件事写进了说明书的 8.2.1。

### 2.3 三处把规则写进界面的地方

原型最容易做成"看起来漂亮但没规则"的图。这次我们逼自己做到：每个交互点都要能回答"什么条件下这个按钮不能点、点了会发生什么、失败了用户看到什么"。

**（一）集市页的三种非正常状态**

F02b / F02c / F02d 三个帧分别对应加载中、空结果、加载失败。空结果页给了三个出口：重置筛选、切换校区、关闭"仅看可邮寄"。**不给出口的空页面等于把用户困住。** 加载失败页写明"筛选条件已保留"，因为用户最怕的是重新选一遍校区和价格。

**（二）智能找物的"条件标签"与"缺什么"**

F04 把模型解析出的条件显示成一排可删除的标签（校区：大学城｜预算：≤300｜分类：显示器）。用户点 × 就能去掉某个条件重新搜，不用重新说一整句话。

每张推荐卡片下方标出「符合：大学城、300 以内」与「缺：未填写成色」。这个"缺什么"不是客套——需求文档 AC-05 明确要求"没有符合条件的商品时明确提示，不编造、不自行放宽硬条件"，而卡片上标出缺失项，是让用户在结果里自己判断"这个能不能接受"，而不是由模型替他决定。

F04b 是无命中帧，文案写死一句话：**不放宽条件、不跨校区凑数、不推荐相似品**。这条约束在界面上是文案，在代码里是硬条件，在测试里是验收项，三处必须一致。

**（三）聊天的打码与交换入口**

F08 的聊天变体里，手机号显示为 `138****5678`，下方紧跟一个「申请交换联系方式」按钮。点击后进入填写表单——注意，**这里是让用户填自己的号码，而不是从聊天记录里提取**，原因见第一节第三条。

交换成功后按钮变成「已交换 · 可关闭」，关闭后立即恢复打码。这个"可关闭"是 AC-15 明确要求的，也是我们在数据库里单独建 `contact_exchange` 表的原因：同意和关闭是两个动作，必须各有各的记录。

### 2.4 原型走查

界面做完不等于流程通。我们按 20 帧逐页走查了一遍，产出《原型走查记录》，记录了每帧的跳转目标、按钮禁用条件、异常文案，以及走查中发现的问题。走查最有价值的部分不是"发现问题 12 个"这种数字，而是发现**原型和接口契约打架**：原型首页展示了已预订商品，而接口文档只返回在售商品。这个冲突最后改的是设计文档（集市列表返回在售 + 已预订，已预订置灰），因为让商品凭空消失比让用户看到"已被预订"更糟糕。

走查记录与 UI 侧的修复核对说明都在仓库 `docs/` 下，可以对照看一轮问题是怎么闭环的。

## 三、概要设计

### 3.1 架构：智能体和页面是两个平级的入口

系统分五层：表现层、接入层、业务服务层、智能体层、数据层。这张图（图 2-2）里有一处是我们特意画出来的约束——

**智能体层不直连数据库，它只调用业务服务层的接口。**

原因在验收标准里：AC-03 要求"输入「大学城校区 300 元以内的显示器」，能提取条件并返回对应在售商品"，AC-06 要求"推荐卡片可打开真实商品详情，价格、校区、履约方式与状态与商品数据一致"。如果让智能体自己去查库，两个入口的过滤规则、状态范围、权限校验迟早会分叉，变成"页面搜不到、AI 搜得到"，或者卡片上写的状态跟详情页不一致。共用业务服务之后，两个入口的数据来源、字段取值、硬条件执行方式是同一份代码，差别只在于智能体多了一层"把自然语言翻译成条件"。

技术选型上，前端 Vue 3 + TypeScript + Vite + Element Plus，后端 Python 3.10 + FastAPI，数据库 MySQL 8.0，消息用 WebSocket，图片走对象存储。选 FastAPI 而不是 Spring Boot，理由和第一次作业一致：智能体的工具调用、流式输出用 Python 写起来短，团队里叶浚轩只熟 Python，换 Java 等于让一个人扛整个智能体层。

**活动图里最值得看的是"模型在哪里必须停下来问人"。** 智能发布的活动图（图 2-6）里有一条分支：模型解析出标题、价格、分类后，如果缺"成色、校区、履约方式"中的任何一项，就返回 `missingFields` 让用户补，**绝不替用户编**。图上写着「不允许 AI 自行编造成色、型号」——这句话在代码里是一段校验，在验收标准里落在 AC-07 的"卖家修改并确认后才正式发布"上：AI 生成的东西必须经人过一遍手，不能让模型的猜测直接变成商品属性。

**时序图里最重要的是失败分支。** 并发抢单的时序图（图 2-7）画了五条生命线：买家 A、买家 B、TradeService、`trade` 表、`product` 表。买家 B 的 `INSERT` 撞唯一键，数据库返回 1062，服务层翻译成 409 `PRODUCT_LOCKED`，文案是"手慢了，该商品已被预订"。这条失败路径和成功路径一样重要——**并发设计的正确性，恰恰体现在失败方收到什么。**

**类图定了一条纪律：只有服务类能改实体状态。** 实体类（Product、Trade）只承载数据与合法性判断，不做业务流转；TradeService 是唯一能改交易状态的角色；智能体工具层是薄适配层，只做参数转换和校验，不含业务规则。这条纪律让"状态被谁改了"永远只有一个答案。

### 3.3 数据库设计

**16 张表，分四组：**

| 分组 | 表 |
|---|---|
| 基础配置 | `campus`、`category` |
| 用户与身份 | `user`、`user_profile` |
| 商品与检索 | `product`、`product_image`、`favorite` |
| 交互与交易 | `conversation`、`message`、`contact_exchange`、`block`、`trade`、`report`、`chat_access_grant`、`admin_audit_log`、`agent_session` |

概念模型层面是 14 个核心实体，落到物理表是 16 张——多出的 `chat_access_grant`（管理员查看聊天的按次授权）与 `agent_session`（智能体多轮条件继承）是两张支撑表，不参与业务建模，但不能省。**这里要澄清一个我们自己在沟通中出现过的口误：不是 17 张。**

**并发唯一性怎么落地（这是全篇技术上最硬的一条）：**

`trade` 表加一个生成列，只在交易已确认时取商品 ID，其余情况为 NULL：

```sql
confirmed_product_id BIGINT UNSIGNED
  GENERATED ALWAYS AS (IF(status = 'confirmed', product_id, NULL)) STORED,
UNIQUE KEY uk_confirmed_product (confirmed_product_id)
```

同一商品只能存在一条 `confirmed` 交易，第二条插入直接撞唯一键。应用层捕获 1062 返回 409，不做"先查后改"。

为什么不写 `UNIQUE (product_id, status)`——因为那样同一商品可以有多条"已取消"，不会冲突，但也会挡住"取消后重新上架再成交"的场景；而生成列只在 confirmed 时生效，取消后生成列变 NULL，不参与唯一性判断，商品可以重新交易。**这个细节决定了一个商品能不能被重复卖出又重复上架。**

**联系方式为什么单独建表：**

如果按最省事的做法，交易确认后直接把号码给买家，能省一张表。但我们没这么做，三个原因：一是成交了还要号码干嘛，真正需要联系是在成交前问成色、约时间；二是 AC-15 要求"双方都同意"和"任一方可随时关闭"，砍掉表这两个机制就没了；三是这张表正是解决"原文不落库后号码从哪来"的钥匙。

| `AgentSession` | `agent_session` | `id` | 存已确认条件，支撑多轮增量 |

完整字段、索引、约束与 DDL 见《数据库设计说明书》，本文不重复。

### 3.4 十条设计决策

说明书 2.6 节记了十条决策，每条都写了"理由、代价、关联哪条验收标准"。举三条代价明确的：

| 决策 | 选择 | 代价（我们认了） |
|---|---|---|
| D-05 | 交易先到先得，不设卖家二次确认 | 卖家无法挑买家，可能被恶意下单锁货 |
| D-06 | 聊天敏感信息写入即打码，不保存原文 | 打码不可逆，举报时无法还原原文作为证据；只能靠"被举报方主动提交"或依法调取 |
| D-10 | 大模型失败时降级为关键词 + 硬条件检索 | 降级结果的推荐解释质量下降，界面须明示"已降级" |

**主动写清代价的设计文档，和只描述功能的设计文档，不是一回事。** 评审如果问"你这个设计有什么问题"，我们希望答案是翻开 2.6 节，而不是现场想。

### 4.3 协作过程

**用 Git 分支管，不用微信群传文件。** 约定是 `feat/你的部分` → `develop`，一人 review 后合，`main` 永远保持可演示状态。这条规矩第一周就立了，因为文件传来传去最后一定会有三个版本的"最终版"。

**每人至少一个自己的提交。** 这一条是硬要求，不是形式主义——助教按人查贡献，代提交等于白做。设计阶段我们踩过一次：有一位成员的稿件由别人代提交，结果她在主分支上一个 commit 都没有，后来补了一次正式合并才把记录补回来。这件事写进了团队待办清单，提醒所有人：**自己提交，这一步谁也替代不了。**

**文档全部 Markdown 入库。** 两份说明书、走查记录、接口约定、图形源码（`.puml`）都在仓库里，改了什么 Git 有记录。导出 PDF 用仓库里的 `tools/` 脚本（Markdown → DOCX → PDF），任何人拉下来都能重新生成，不依赖谁的电脑。

**设计阶段开了两次对齐会。** 第一次定交易流程（先到先得 vs 卖家确认），第二次过接口契约（三条路径与需求文档不一致、`sessionId` 缺失、`contact_exchange` 该不该砍）。两次会的结论都写进了说明书的附录 A，会上争的东西不落到文档里，下次还会再争一遍。

## 八、这次设计阶段没做完的事

设计阶段最大的收获不是交付了多厚的文档，而是**把"当时觉得没问题"的话一条条逼到墙角**。上面这三条，比前面写的任何一条设计都更值得记下来——它们是接下来两周真正要干的事。
