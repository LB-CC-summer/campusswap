### 2.2 统一响应外壳

所有接口返回同一结构，前端只写一套解析器。

| 字段 | 类型 | 必返 | 说明 |
|---|---|---|---|
| `code` | int | 是 | 恒等于 HTTP 状态码 |
| `msg` | string | 是 | 可直接展示给用户的中文文案 |
| `data` | object / null | 是 | 失败时为 `null` |
| `bizCode` | string | 否 | 业务原因细分；成功时不返回该键 |
| `traceId` | string | 否 | 排障用，前端不展示 |

```python
# app/schemas/common.py
from typing import Any, Optional
from pydantic import BaseModel
from fastapi import HTTPException

class Result(BaseModel):
    code: int = 200
    msg: str = "success"
    data: Any = None
    bizCode: Optional[str] = None
    traceId: Optional[str] = None

def fail(status: int, msg: str, biz_code: str | None = None) -> HTTPException:
    return HTTPException(
        status_code=status,
        detail={"code": status, "msg": msg, "bizCode": biz_code, "data": None},
    )
```

```python
# app/main.py —— 把 HTTPException 的 detail 原样输出，保证外壳一致
@app.exception_handler(StarletteHTTPException)
async def http_exception_handler(request: Request, exc: StarletteHTTPException):
    detail = exc.detail if isinstance(exc.detail, dict) else {
        "code": exc.status_code, "msg": str(exc.detail), "data": None
    }
    return JSONResponse(status_code=exc.status_code, content=detail)
```

### 2.3 错误码总表

| HTTP | bizCode | 含义 | 触发接口 |
|---|---|---|---|
| 400 | `INVALID_PARAM` | 参数缺失或越界 | 全部写接口 |
| 401 | `UNAUTHORIZED` | 未登录 / Token 失效 | 需登录接口 |
| 403 | `NO_PERMISSION` | 无该操作的权限 | 后台接口 |
| 403 | `NOT_PARTICIPANT` | 不是该会话或交易的参与者 | 消息、联系方式 |
| 403 | `CANNOT_BUY_OWN` | 不能购买自己发布的商品 | 立即购买 |
| 404 | `PRODUCT_NOT_FOUND` | 商品不存在 | 详情、购买 |
| 404 | `TRADE_NOT_FOUND` | 交易单不存在 | 交易、联系方式 |
| 404 | `CONVERSATION_NOT_FOUND` | 会话不存在 | 消息、联系方式 |
| 409 | `PRODUCT_LOCKED` | 商品已被他人抢先预订（捕获 1062） | 立即购买 |
| 409 | `ORDER_DUPLICATED` | 本人对该商品已有 `confirmed` 交易 | 立即购买 |
| 409 | `TRADE_STATUS_CONFLICT` | 交易当前状态不允许该操作 | 取消 / 完成 |
| 409 | `EXCHANGE_ALREADY_ACTIVE` | 该会话已有未关闭的联系方式申请 | 联系方式申请 |
| 409 | `GRANT_ALREADY_ACTIVE` | 该举报已有生效中的查看授权 | 后台授权 |
| 429 | `RATE_LIMITED` | 超出频控阈值 | 智能检索 |
| 500 | `SERVER_ERROR` | 未捕获的服务端异常 | 全部 |
| 502 | `UPSTREAM_ERROR` | 大模型返回异常（已降级则不返回该码） | 智能检索 |
| 504 | `UPSTREAM_TIMEOUT` | 大模型超时（已降级则不返回该码） | 智能检索 |

> **前端只认 `bizCode`**：`code` 与 HTTP 码一致，仅用于拦截器判断登录态（401）与频控（429）；具体原因一律 `switch (bizCode)`。不提供字符串形式的错误码结构。

### 2.4 分页、排序与字段约定

1. 分页参数 `page` 从 1 开始，`pageSize` 默认 20、上限 50；响应含 `total` / `page` / `pageSize` / `list`。
2. 金额：库内 `DECIMAL(10,2)`，**接口输出为两位小数的字符串**（`"1800.00"`），避免 JSON 数字丢尾零。
3. 时间：库内无时区 UTC，接口输出带 `+08:00` 的 ISO 8601（`2026-11-22T10:12:31.220+08:00`）。
4. 字段命名：对外小驼峰，库内下划线，Pydantic `alias` 映射（见附录 A）。
5. 布尔：`true` / `false`，不用 0 / 1。
6. 空集合返回 `[]` 而非 `null`。

### 4.2 商品列表

`GET /api/product/list` ｜ 公开 ｜ 只读

**Query 参数**

| 字段 | 类型 | 必填 | 约束 | 说明 |
|---|---|---|---|---|
| `campusId` | int | 是 | — | 校区为硬条件，不传则返回 400 |
| `categoryId` | int / null | 否 | — | 类目筛选 |
| `priceMax` | string / null | 否 | 两位小数 | 价格上限 |
| `keyword` | string / null | 否 | ≤50 | 标题模糊匹配 |
| `status` | string / null | 否 | `on_sale` / `reserved` | 默认 `on_sale` + `reserved`（见下） |
| `supportMail` | bool / null | 否 | — | 仅看支持邮寄（跨市场景） |
| `page` / `pageSize` | int | 否 | 见 2.4 | 分页 |

**成功响应**

```json
{
  "code": 200, "msg": "success",
  "data": {
    "total": 17, "page": 1, "pageSize": 20,
    "list": [
      {
        "productId": 1001, "title": "24寸 1080P 显示器", "price": "650.00",
        "coverUrl": "https://cdn.campusswap.com/product/1001_1.jpg",
        "campusId": 3, "campusName": "大学城", "categoryName": "数码",
        "status": "on_sale", "buyDisabled": false,
        "supportMail": false, "publishedAt": "2026-11-20T19:04:12.000+08:00"
      },
      {
        "productId": 1005, "title": "闲置自行车", "price": "180.00",
        "coverUrl": "https://cdn.campusswap.com/product/1005_1.jpg",
        "campusId": 3, "campusName": "大学城", "categoryName": "出行",
        "status": "reserved", "buyDisabled": true,
        "supportMail": true, "publishedAt": "2026-11-19T09:31:40.000+08:00"
      }
    ]
  }
}
```

**状态过滤口径（须严格执行）**

1. 列表同时返回 `on_sale` 与 `reserved`。`reserved` 商品**不隐藏**——先到先得下若过滤掉已预订商品，商品会凭空消失，且原型 F02 已展示 2 件已预订商品；
2. `reserved` 项前端**置灰、购买按钮禁用**，响应中用 `buyDisabled: true` 明确告知，前端不必自己判断；
3. `draft` / `sold` / `removed` 一律不返回；
4. **智能检索是例外**：`/api/ai/search` 只返回 `on_sale`（见 4.4），因为检索的产品语义是「帮我找能买的」。

**实现要点**

```sql
-- 走 idx_market(status, campus_id, category_id, published_at)
SELECT ... FROM product
WHERE status IN ('on_sale','reserved')
  AND campus_id = ?
ORDER BY published_at DESC
LIMIT ? OFFSET ?;
```

`coverUrl` 取 `product_image` 中 `sort_no` 最小的那条，用一次子查询或窗口函数聚合，禁止 N+1。

### 4.3 商品详情

`GET /api/product/{productId}` ｜ 公开 ｜ 只读

**响应 `data`**

```json
{
  "productId": 1001, "title": "24寸 1080P 显示器",
  "description": "宿舍毕业出，屏幕无坏点……",
  "price": "650.00", "status": "reserved", "buyDisabled": true,
  "campusId": 3, "campusName": "大学城", "categoryId": 4, "categoryName": "数码",
  "supportMail": false, "viewCount": 37,
  "seller": { "sellerId": 1004, "nickname": "小林", "verifiedStatus": "student" },
  "images": [ { "url": "https://cdn.campusswap.com/product/1001_1.jpg", "sortNo": 0 } ],
  "attributes": { "接口": "HDMI", "屏幕": "24寸" },
  "missingFields": ["成色"],
  "publishedAt": "2026-11-20T19:04:12.000+08:00"
}
```

**要点**

1. `attributes` **只返回已填写的键**，不返回 `null` 占位；缺失信息由 `missingFields` 表达，两者语义不重叠。
2. `missingFields` 取值限于 `成色` / `实拍图` / `描述` / `校区` / `价格`，用于详情页「信息不完整」提示；与智能检索的 `missingFields` **同名同语义**，前端一套渲染逻辑复用。
3. `viewCount` 自增用 `UPDATE ... SET view_count = view_count + 1`，不与读取同事务，允许近似值。
4. 不存在的 `productId` 返回 404 `PRODUCT_NOT_FOUND`。

### 4.4 智能检索（多轮 + 降级 + 限流）

`POST /api/ai/search` ｜ 登录 ｜ 只读

**接口描述**：自然语言 → 大模型解析为结构化条件（含 `purpose` 用途）→ 与 `sessionId` 的历史条件合并 → 查 `product` → 对候选生成匹配标签、缺失字段与推荐理由。模型不可用时降级为关键词 `LIKE`，返回 `degraded: true`。

**请求 Body**

| 字段 | 类型 | 必填 | 约束 | 说明 |
|---|---|---|---|---|
| `sessionId` | string / null | 否 | ≤32 | 不传则新建会话；传了则继承该会话已确认条件 |
| `query` | string | 是 | 1–200 | 本轮自然语言 |
| `page` / `pageSize` | int | 否 | 见 2.4 | 分页 |

**请求示例**

```json
{ "query": "找一台2000以内的二手显示器，大学城校区" }
```

```json
{ "sessionId": "12", "query": "再便宜点，1500 以内" }
```

**成功响应**

```json
{
  "code": 200, "msg": "success",
  "data": {
    "sessionId": "12", "degraded": false,
    "conditions": {
      "campusId": 3, "campusName": "大学城", "categoryId": null,
      "priceMax": "1500.00", "keyword": "显示器", "purpose": "编程"
    },
    "total": 4, "page": 1, "pageSize": 20,
    "list": [
      {
        "productId": 1002, "title": "24寸 1080P 显示器，宿舍毕业出",
        "price": "650.00", "coverUrl": "https://cdn.campusswap.com/product/1002_1.jpg",
        "campusId": 3, "campusName": "大学城", "status": "on_sale",
        "matchedTags": ["显示器", "1080P", "1500元以内", "大学城"],
        "missingFields": ["成色", "实拍图"],
        "explanation": "标题命中「显示器」，650 元在你 1500 元预算内且同在大学城；但未填成色、无实拍图，建议先问屏幕磨损。"
      }
    ]
  }
}
```

| 字段 | 说明 |
|---|---|
| `sessionId` | 首次由后端生成（写入 `agent_session`），续聊沿用；**前端必须回传** |
| `degraded` | `true` 表示走了关键词降级，`conditions` 只含 `keyword`，`explanation` 为模板文案 |
| `conditions.campusId` | `int \| null`，`null` = 不限校区；**不接受字符串 `"all"`** |
| `conditions.purpose` | `编程` / `考研` / `设计` / `游戏` / `日常`；只用于排序加权与解释文案，**不参与 SQL 过滤**（库内无此列） |
| `list[].status` | 本接口**恒为 `on_sale`**，`reserved` / `sold` / `draft` / `removed` 不出现 |
| `list[].matchedTags` | 取自合并后 `conditions`、商品标题与 `attributes`，须真实出现过的词 |
| `list[].explanation` | ≤60 字，只能引用给定字段，禁止编造品牌、型号、成色 |

**失败响应**

```json
{ "code": 429, "msg": "操作太频繁，请 10 秒后再试", "bizCode": "RATE_LIMITED", "data": null }
```

```json
{ "code": 400, "msg": "query 不能为空，且长度不超过 200 字符", "bizCode": "INVALID_PARAM", "data": null }
```

> 降级成功后仍返回 **200 + `degraded: true`**；只有降级查询本身也失败才返回 500。

**实现要点**

**① 会话落库（`agent_session` 表，不使用进程内字典）**

```python
def get_or_create_session(db: Session, user_id: int, session_id: str | None) -> AgentSession:
    if session_id:
        s = db.get(AgentSession, int(session_id))
        if s and s.user_id == user_id and s.status == "active":
            return s                      # 仅本人可续用，防止会话串号
    s = AgentSession(user_id=user_id, context={}, status="active")
    db.add(s); db.commit(); db.refresh(s)
    return s
```

落库而非内存的理由：多 worker 与热重载下内存字典会丢上下文；`agent_session` 已在《02》建表（16 张表之一），成本仅为一次读写。

**② 条件合并：新值覆盖、空值忽略**

```python
def merge_conditions(old: dict, new: dict) -> dict:
    merged = dict(old)
    for k, v in new.items():
        if v is None or v == "":
            continue            # 本轮没提到，保留上一轮
        merged[k] = v           # 本轮提到，覆盖（priceMax 2000 → 1500）
    return merged
```

**③ 限流：会话内消息条数 + 用户级滑窗双上限**

```python
_WINDOW, _LIMIT = 10.0, 3      # 同一用户 10 秒最多 3 次
_SESSION_MAX_TURNS = 10        # 同一会话最多累积 10 轮，超出提示重新开始

def check(user_id: int) -> None:
    now = time.monotonic()
    with _lock:
        q = _HITS[user_id]
        while q and now - q[0] > _WINDOW:
            q.popleft()
        if len(q) >= _LIMIT:
            raise fail(429, "操作太频繁，请 10 秒后再试", "RATE_LIMITED")
        q.append(now)
```

两级上限分别对应「防刷模型」（用户级）与「防会话无限膨胀」（会话级），都写进 `agent_session.context` 的轮次计数。单进程内有效，多实例需换 Redis（见 6.1）。

**④ 降级**

```python
try:
    cond = await parse_query(body.query)         # httpx, timeout=5s
except (httpx.TimeoutException, httpx.HTTPError, ValueError):
    cond = AiCondition(keyword=body.query[:50])  # 原句作关键词
    degraded = True
```

**⑤ 解释字段由第二次模型调用生成，后端必须校验**

解析条件那一次只输出 `conditions`；拿到候选后再调一次，让模型对每个候选给出 `matchedTags` / `missingFields` / `explanation`。Prompt 固定返回结构，且后端不信模型：

1. `productId` 不在候选集合 → 丢弃；
2. `matchedTags` 不在标题或 `attributes` 中出现 → 剔除；
3. `missingFields` 不在白名单（成色/实拍图/描述/校区/价格）→ 剔除；
4. `explanation` 超 60 字 → 截断。

降级时不调第二次模型，改用模板：`按「{keyword}」为你找到，价格 {price} 元。`

**失败响应**

```json
{ "code": 409, "msg": "手慢了，该商品已被预订", "bizCode": "PRODUCT_LOCKED", "data": null }
```

| bizCode | HTTP | 触发条件 | 前端处理 |
|---|---|---|---|
| `PRODUCT_LOCKED` | 409 | 捕获 MySQL 1062（商品已被他人抢先） | 提示「手慢了」并返回集市 |
| `ORDER_DUPLICATED` | 409 | 本人对该 `productId` 已有 `confirmed` 交易 | 跳「我的交易」 |
| `CANNOT_BUY_OWN` | 403 | 买家 = 卖家 | 不展示购买按钮 |
| `PRODUCT_NOT_FOUND` | 404 | 商品不存在 | 返回集市 |
| `INVALID_PARAM` | 400 | `productId` 缺失或非正整数 | 前端兜底 |

其余失败场景：商品为 `draft` / `sold` / `removed` → 409 `TRADE_STATUS_CONFLICT`（商品当前不可购买）。

**核心代码**

```python
# 1. 先区分「本人重复提交」：仅用于错误文案，不承担并发判定
dup = db.query(Trade).filter(
    Trade.buyer_id == user.id,
    Trade.product_id == body.productId,
    Trade.status == "confirmed",
).first()
if dup:
    raise fail(409, "你已购买过该商品，请到「我的交易」查看", "ORDER_DUPLICATED")

product = db.get(Product, body.productId)
if product is None:
    raise fail(404, "商品不存在", "PRODUCT_NOT_FOUND")
if product.seller_id == user.id:
    raise fail(403, "不能购买自己发布的商品", "CANNOT_BUY_OWN")
if product.status not in ("on_sale", "reserved"):
    raise fail(409, "该商品当前不可购买", "TRADE_STATUS_CONFLICT")

# 2. 并发判定交给唯一索引，不先查后改、不用 SELECT ... FOR UPDATE
try:
    trade = Trade(product_id=product.id, buyer_id=user.id, seller_id=product.seller_id,
                  status="confirmed", confirmed_at=datetime.now(timezone.utc))
    db.add(trade)
    product.status = "reserved"          # 展示态，不承担并发控制
    db.commit()
    db.refresh(trade)
except IntegrityError as e:
    db.rollback()
    if getattr(getattr(e, "orig", None), "errno", None) == 1062:
        raise fail(409, "手慢了，该商品已被预订", "PRODUCT_LOCKED")
    raise fail(500, "下单失败，请稍后再试", "SERVER_ERROR")
```

**要点**

1. 唯一性由 `uk_confirmed_product`（生成列 `confirmed_product_id`）在 `INSERT` 时裁决，后到者**阻塞在唯一索引项**上，待先到者提交后才收到 1062；先到者若回滚，后到者反而成功。因此失败文案不能写成「立即被抢」，前端提示应为「手慢了」。
2. 上面的 `dup` 查询**不是并发控制**，只是为了把「本人重复」与「被他人抢走」分开；并发正确性完全由唯一索引保证，与《07》的 6.1 一致。
3. `trade.status='confirmed'` 同时是联系方式交换的放行条件，两处共用同一状态语义。
4. 事务里必须同时写 `trade` 与 `product.status='reserved'`，缺一步会出现「交易已确认、商品仍在售」。

### 4.6 取消 / 完成交易

`POST /api/trade/{tradeId}/cancel`、`POST /api/trade/{tradeId}/complete` ｜ 登录（须为参与方）

**取消**：Body `{ "reason": "约不上时间" }`（≤200 字）。交易置 `cancelled`，商品回 `on_sale`，`confirmed_product_id` 自动回到 `NULL`，同事务完成。

**完成**：无 Body。交易置 `completed`、商品置 `sold`，同事务。

**失败码**：403 `NOT_PARTICIPANT`（非参与方）、404 `TRADE_NOT_FOUND`、409 `TRADE_STATUS_CONFLICT`（当前状态不允许该操作，例如已取消的交易不能再完成）。

**要点**：状态流转语句必须带前置状态，影响行数为 0 即视为冲突并回滚（`UPDATE trade SET status='cancelled' WHERE id=? AND status='confirmed'`），与《07》的 T2 / T3 迁移规则一致。

### 4.7 消息列表

`GET /api/message/list?conversationId=5001&page=1` ｜ 登录（须为会话参与方）

```json
{
  "code": 200, "msg": "success",
  "data": {
    "conversationId": 5001, "total": 32, "page": 1, "pageSize": 50,
    "list": [
      {
        "messageId": 8001, "senderId": 1004, "type": "text",
        "content": "同学，这个显示器还在吗？我手机号 [联系方式已隐藏，可申请交换]",
        "createdAt": "2026-11-22T09:12:33.120+08:00"
      }
    ]
  }
}
```

**要点**

1. `message.content` **入库前已打码**，接口直接返回，不再做正则，也不做「已打码」标记。
2. 校验条件为 `当前用户 ∈ {conversation.buyer_id, conversation.seller_id}`，缺一不可；失败 403 `NOT_PARTICIPANT`。
3. 按 `(conversation_id, id)` 倒序取 50 条，返回前翻正序。
4. 读接口不改未读数；未读数在「进会话」的写接口里清零（与《02》的 `conversation` 未读列同事务）。

### 4.8 联系方式交换（申请 → 同意 → 展示 / 关闭）

联系方式**原文不落库**：`message` 里出现即打码；号码的唯一来源是用户自己在交换表单里填写，加密存入 `contact_exchange`（《02》第 10 张表）。

**① 申请**：`POST /api/contact/apply` ｜ 登录（会话参与方）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `conversationId` | int | 是 | 会话 ID |
| `phoneEnc` | string | 是 | 前端用平台公钥加密的号码，后端解密后 AES-GCM 加密入库 |

```json
{ "code": 200, "msg": "申请已提交，等待对方同意",
  "data": { "exchangeId": 3001, "status": "pending" } }
```

失败：403 `NOT_PARTICIPANT`、404 `CONVERSATION_NOT_FOUND`、409 `EXCHANGE_ALREADY_ACTIVE`（该会话已有 `pending` 或 `active` 申请，须先关闭）。

**② 同意**：`POST /api/contact/{exchangeId}/accept` ｜ 登录（被申请方）

```json
{ "code": 200, "msg": "success",
  "data": { "exchangeId": 3001, "status": "active",
            "counterpartPhone": "13812345678",
            "counterpartNickname": "小林" } }
```

**③ 关闭**：`POST /api/contact/{exchangeId}/close` ｜ 任一方

关闭后 `status='closed'`，`closed_at` 记录时间，**立即失效**：此后再调 accept 或查询一律 409 `TRADE_STATUS_CONFLICT`。

**要点**

1. 只有 `status='active'` 且未关闭才返回明文；`pending` 阶段申请方自己填的号码也不回显。
2. `phoneEnc` 在服务端解密为明文再 AES-256-GCM 加密存 `VARBINARY(255)`；密钥走环境变量 `PHONE_AES_KEY`，不进仓库。
3. 明文只在 accept 响应里出现一次，**不写日志、不进异常堆栈**。
4. 「双方同意」与「可随时关闭」是 AC-15 的两个判定点，缺任一机制都算不满足。

### 4.10 后台：申请查看聊天片段

**① 申请**：`POST /api/admin/chat-access/apply` ｜ 管理员

### 4.11 发布确认 / 保存草稿

`POST /api/product/create` ｜ 登录（卖家）

**草稿的存放位置（本设计明确口径）**

AI 智能发布产生的草稿**不入库**：识别出的类目、属性与追问结果全部存在 `agent_session.context` 里，用户确认前 `product` 表不产生任何记录。这一口径与《01》§3.5（「草稿只存在会话上下文，确认后才写商品表」）和 AC-07 的判定方式（「检查确认前商品表无记录」）一致。

`product.status` 的 `draft` 值因此**只服务于用户手动保存的草稿**：卖家编辑到一半点「保存草稿」，此时才在 `product` 表建行并置 `draft`。这类草稿只在「我的发布」可见，不进集市、不进检索、不能被购买。

**请求 Body**

| 字段 | 类型 | 必填 | 约束 | 说明 |
|---|---|---|---|---|
| `title` | string | 是 | 1–80 | 标题 |
| `description` | string | 否 | ≤2000 | 描述，提交前做联系方式过滤 |
| `price` | string | 是 | 两位小数，≥0 | 金额 |
| `categoryId` | int | 是 | — | 类目 |
| `campusId` | int | 是 | — | 校区 |
| `supportMail` | bool | 否 | 默认 `false` | 是否支持邮寄（跨市场景必备） |
| `attributes` | object | 否 | — | 类目差异属性，如 `{"接口":"HDMI"}` |
| `images` | string[] | 否 | ≤9 | 图片 URL，须已上传至对象存储 |
| `status` | string | 否 | `on_sale` / `draft`，默认 `on_sale` | `on_sale` = 确认发布；`draft` = 手动存草稿 |

```json
{ "code": 200, "msg": "发布成功",
  "data": { "productId": 1006, "status": "on_sale", "publishedAt": "2026-11-22T11:30:00.000+08:00" } }
```

```json
{ "code": 200, "msg": "草稿已保存",
  "data": { "productId": 1007, "status": "draft", "publishedAt": null } }
```

**失败码**：400 `INVALID_PARAM`（必填项缺失、价格越界、类目属性不合法）、403 `NO_PERMISSION`（账号被禁用）、404 `NOT_FOUND`（类目或校区不存在）。

**要点**

1. 标题与描述提交时做联系方式过滤，命中即拒绝并提示「请勿在描述中填写联系方式」，**不静默打码后放行**——发布场景要用户自己改。
2. `status='on_sale'` 时写入 `published_at`；`draft` 时为 `NULL`，集市与检索均以 `published_at IS NOT NULL` 与状态双重过滤。
3. `categoryId` 对应的类目必填属性（来自 `get_category_schema`）缺失时不拦截，由前端的「信息不完整」提示承接，与 4.3 的 `missingFields` 同一套语义。
