## 1 引言

### 1.1 编写目的

本文档定义校易集 CampusSwap 的数据库设计，供三类读者使用：

- **开发人员**：按第 4 章的字段定义实现 ORM 模型与接口，不再另行约定字段名；
- **测试与验收人员**：按第 6 章的权限矩阵、第 7 章的查询预期、附录 C 的验收对照表逐条核对；
- **评审与助教**：通过第 3 章的概念模型与附录 A 的关系模式，判断设计与需求是否一致。

本文档与《软件需求规格说明书》的 7.9（隐私与安全设计）、7.10（交易流程）严格对应，凡是需求里出现的"状态""权限""脱敏"，在第 4 章都能找到承载它的字段或约束。

### 1.2 范围

覆盖二期迭代所需的全部持久化对象：

- **实体**：14 个概念实体（校区、用户、用户资料、分类、商品、商品图片、收藏、会话、消息、联系方式交换、拉黑、交易、举报、智能体会话）；
- **支撑表**：2 张（聊天片段查看授权 `chat_access_grant`、后台审计日志 `admin_audit_log`），它们不是业务概念，而是需求 7.9.4「按次授权、全程留痕」的直接产物；
- 共计 **16 张表**。

不包含：缓存（Redis）、对象存储中的图片文件本身、日志文件。这些在《系统设计说明书》的部署章节说明。

## 2 数据库环境

### 2.1 运行环境

| 项 | 取值 | 说明 |
| --- | --- | --- |
| DBMS | MySQL 8.0.16 及以上 | 需要 CHECK 约束（8.0.16 起生效）与生成列（8.0.13 起） |
| 存储引擎 | InnoDB | 事务、行锁、外键；`trade` 的并发控制依赖行锁 |
| 字符集 | `utf8mb4` / `utf8mb4_0900_ai_ci` | 商品标题、聊天内容会出现 emoji，`utf8` 三字节存不下 |
| 时区 | 库内 UTC，接口出口 +08:00 | 避免跨时区展示错位 |
| 隔离级别 | `REPEATABLE READ`（默认） | 抢单靠唯一索引在 INSERT 时判定，不依赖隔离级别 |
| 连接池 | SQLAlchemy Pool，size=10，overflow=20 | 课程项目并发量小，够用 |

**选型说明**：团队已有 MySQL 使用经验，课程环境提供现成实例，云服务器上一行 `docker run` 即可起库；MySQL 8 的生成列、CHECK 约束与 JSON 类型足以支撑本项目的"部分唯一索引"与"类目属性"需求，因此不引入 PostgreSQL。代价是缺少部分索引与数组类型，这两点已用生成列和 JSON 列等价实现，见 5.2。

### 2.2 部署与初始化

```bash
mysql -u root -p -e "CREATE DATABASE campusswap DEFAULT CHARSET utf8mb4 COLLATE utf8mb4_0900_ai_ci;"
mysql -u root -p campusswap < db/schema.sql    # 16 张表
mysql -u root -p campusswap < db/seed.sql      # 五校区 + 分类 + 测试账号 + 演示商品
```

执行后应得到 16 张表，`SELECT COUNT(*) FROM information_schema.tables WHERE table_schema='campusswap'` 返回 16。种子脚本里的账号密码为占位值，首次部署后必须用后端脚本重置为真实 BCrypt 值，仓库中不出现可用口令。

### 2.3 命名与编码约定

| 约定 | 做法 | 原因 |
| --- | --- | --- |
| 表名、列名 | 小写下划线（`snake_case`），表名用单数 | 与 SQL 习惯一致，避免大小写敏感问题 |
| 主键 | 统一 `id`，`BIGINT UNSIGNED AUTO_INCREMENT` | 类型统一，便于 ORM 泛型处理 |
| 外键列 | `<实体>_id`，如 `seller_id`、`campus_id` | 见名知义，join 时不歧义 |
| 布尔列 | `is_` / `allow_` / `support_` 前缀，`TINYINT(1)` | 与 ORM 的 boolean 直接对应 |
| 时间列 | `_at` 后缀，`DATETIME(3)` | 毫秒精度，消息排序不出现同秒歧义 |
| 金额列 | `DECIMAL(10,2)` | 禁止 FLOAT，避免 0.1+0.2 误差 |
| 状态列 | `status`，`ENUM` 类型 | 值域写进表结构，应用层写错直接被数据库拒绝 |
| 接口输出 | 驼峰（`camelCase`），由 Pydantic `alias_generator` 转换 | 前端零映射；库内仍保持 SQL 习惯 |

## 3 概念设计

### 3.1 实体识别

从需求文档的用例出发，把"需要长期保存、且有独立生命周期"的名词抽成实体，共 14 个：

| 类别 | 实体 | 识别依据 |
| --- | --- | --- |
| 主数据 | 校区 Campus | 五校区可后台增删，是筛选与履约的硬条件 |
| 主数据 | 用户 User | 登录、角色、禁用状态 |
| 主数据 | 用户资料 UserProfile | 与登录凭证生命周期不同，且含敏感字段，拆表 |
| 主数据 | 分类 Category | 支持父子层级 |
| 交易对象 | 商品 Product | 状态机主体 |
| 交易对象 | 商品图片 ProductImage | 从属商品，随商品删除 |
| 交易对象 | 收藏 Favorite | 用户与商品的多对多 |
| 沟通 | 会话 Conversation | 商品 + 买家 + 卖家三者唯一 |
| 沟通 | 消息 Message | 从属会话 |
| 沟通 | 联系方式交换 ContactExchange | 有独立状态（待同意/已同意/已关闭），不能塞进消息表 |
| 沟通 | 拉黑 Block | 用户与用户的自反多对多 |
| 成交 | 交易 Trade | 状态机主体，并发控制的焦点 |
| 治理 | 举报 Report | 后台处置入口 |
| 智能体 | 智能体会话 AgentSession | 存多轮对话的已确认条件 |

另有两张支撑表，不对应用户可见的概念，但对需求有直接支撑：

- `chat_access_grant`：需求 7.9.4 要求"管理员默认看不到聊天，仅处理举报时按单次授权查看片段"，这个"授权"本身有生命周期（时间窗、24 小时失效、撤销），必须持久化；
- `admin_audit_log`：处置动作与查看行为都要留痕，且不可删改。

### 3.4 数据规范化

按关系数据库设计范式检查，16 张表均满足第三范式（3NF）：

| 范式 | 要求 | 本设计的满足情况 |
| --- | --- | --- |
| 1NF | 每列不可再分 | 所有列都是原子值；唯一的例外是 `attributes` 与 `context` 两个 JSON 列，见下方"有意的反规范化" |
| 2NF | 非主键列完全依赖于主键 | 除 `favorite`、`block` 这类纯连接表外，每张表都是单一主键；连接表的两个外键共同构成业务唯一性，其余列（如 `created_at`）依赖整行 |
| 3NF | 非主键列不传递依赖于主键 | 校区名、分类名、卖家昵称都不冗余存在 `product` 里，一律通过外键 join 取得；商品表里没有"卖家所在校区"这类可由其他表推出的列 |

**有意的反规范化**，共四处，每处都有明确理由：

| 位置 | 违反的范式 | 保留理由 |
| --- | --- | --- |
| `product.attributes`（JSON） | 1NF | 教材、显示器、自行车的属性完全不同，拆表会得到二十多张稀疏表；本期只展示不筛选，JSON 是成本最低的选择 |
| `agent_session.context`（JSON） | 1NF | 存的是"本次对话已确认的筛选条件"，结构随对话变化，本质是一份状态快照而非关系数据 |
| `conversation.buyer_unread` / `seller_unread` | 3NF | 未读数可由 `message` 统计得出，但列表页要展示十几个会话，逐条统计会造成 N+1 查询；用计数器把读放大换成写放大，是合理的取舍 |
| `product.view_count` | 3NF | 同上，浏览量属于高频写、低频读的统计值，不宜每次 `COUNT` |

这四处都属于"读多写少"的场景，且都有明确的失效边界（如未读数在消息写入时同事务更新），不会出现数据漂移。

### 4.1 campus（校区）

**用途**：五校区的配置表。做成表而不是枚举，是为了后台能新增校区（AC-17）：加一条记录，前端筛选器与发布表单自动出现新选项，不需要改代码、不需要发版。

| 列名 | 类型 | 可空 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| id | BIGINT UNSIGNED | 否 | 自增 | PK |
| name | VARCHAR(32) | 否 | — | 全称，如"大学城校区"，用于详情页、个人中心 |
| short_name | VARCHAR(20) | 否 | — | 简称，如"大学城"，用于筛选器与角标；不做字符串截取 |
| city | VARCHAR(32) | 否 | — | 广州 / 揭阳 |
| is_cross_city | TINYINT(1) | 否 | 0 | 1 = 跨市，只能邮寄（揭阳） |
| sort_no | INT | 否 | 0 | 展示顺序 |
| is_enabled | TINYINT(1) | 否 | 1 | 0 = 停用，不出现在筛选器与发布表单 |
| created_at | DATETIME(3) | 否 | CURRENT_TIMESTAMP(3) | |

**索引**：`uk_campus_name(name)`、`uk_campus_short_name(short_name)` 防重名；`idx_enabled_sort(is_enabled, sort_no)` 供 `GET /api/campuses` 排序。

**设计说明**：`name` 与 `short_name` 同时存在，是因为两种界面语境需要不同长度（"大学城校区"/"大学城"），而中文截取会切出"揭阳校"这类错字。二者都建唯一索引，避免后台录入两个"大学城"。

### 4.2 user（用户）

**用途**：只存登录凭证、角色与账号状态。敏感资料在 `user_profile`，二者生命周期不同（改昵称不应触发密码表写入）。

| 列名 | 类型 | 可空 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| id | BIGINT UNSIGNED | 否 | 自增 | PK |
| email | VARCHAR(64) | 否 | — | 学号邮箱，仅用于校内认证，不对外展示 |
| password_hash | VARCHAR(100) | 否 | — | BCrypt，禁止明文与 MD5 |
| nickname | VARCHAR(32) | 否 | — | 展示名 |
| avatar_url | VARCHAR(255) | 是 | NULL | 头像 |
| role | ENUM('user','admin','super_admin') | 否 | 'user' | 超管才能批准聊天片段授权 |
| status | ENUM('active','disabled') | 否 | 'active' | 禁用后不能登录与操作，但数据保留 |
| disabled_reason | VARCHAR(200) | 是 | NULL | 禁用原因，后台展示 |
| created_at | DATETIME(3) | 否 | CURRENT_TIMESTAMP(3) | |
| last_login_at | DATETIME(3) | 是 | NULL | |

**索引**：`uk_user_email(email)` 一个邮箱一个账号；`idx_status(status)` 供后台按状态筛选。

**设计说明**：`role` 用三值而非布尔，是因为"管理员"与"超级管理员"权限不同——只有超管能批准查看聊天片段（需求 7.9.4）。

### 4.3 user_profile（用户资料）

**用途**：与用户 1:1 的资料表，存放校区、认证状态与手机号密文。

| 列名 | 类型 | 可空 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| user_id | BIGINT UNSIGNED | 否 | — | PK，同时是 FK → user.id，级联删除 |
| campus_id | BIGINT UNSIGNED | 否 | — | FK → campus.id |
| verified_status | ENUM('none','verified') | 否 | 'none' | 只显示"已认证"徽章，不展示学号 |
| phone_enc | VARBINARY(255) | 是 | NULL | 手机号 AES 密文，解密只发生在后端 |
| allow_contact | TINYINT(1) | 否 | 1 | 是否允许他人发起联系方式交换 |
| updated_at | DATETIME(3) | 否 | CURRENT_TIMESTAMP(3) | ON UPDATE |

**索引**：`idx_campus(campus_id)`。

**设计说明**：`user_id` 既是主键又是外键，天然保证 1:1；手机号用 `VARBINARY` 存密文而不是 `VARCHAR` 存明文，是为了让"误查明文"在第 4 章层面就不可能发生。

### 4.4 category（分类）

**用途**：两级分类，类目差异属性放 `product.attributes`，不为每个类目建属性表。

| 列名 | 类型 | 可空 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| id | BIGINT UNSIGNED | 否 | 自增 | PK |
| name | VARCHAR(32) | 否 | — | 分类名 |
| parent_id | BIGINT UNSIGNED | 是 | NULL | FK → category.id，自反；一级分类为 NULL |
| sort_no | INT | 否 | 0 | 排序 |

**索引**：`idx_parent(parent_id)`。

**设计说明**：自反外键 `ON DELETE SET NULL`——父分类被删时子分类降为一级，而不是级联删除商品。

### 4.5 product（商品）

**用途**：核心业务表，承载商品状态机（draft → on_sale → reserved → sold / off_shelf）。

| 列名 | 类型 | 可空 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| id | BIGINT UNSIGNED | 否 | 自增 | PK |
| seller_id | BIGINT UNSIGNED | 否 | — | FK → user.id |
| category_id | BIGINT UNSIGNED | 否 | — | FK → category.id |
| campus_id | BIGINT UNSIGNED | 否 | — | FK → campus.id，筛选的硬条件 |
| title | VARCHAR(80) | 否 | — | 标题 |
| description | TEXT | 是 | NULL | 描述，发布前做联系方式过滤 |
| price | DECIMAL(10,2) | 否 | — | 价格，CHECK ≥ 0 |
| support_mail | TINYINT(1) | 否 | 0 | 是否支持邮寄，跨市场景唯一履约路径 |
| status | ENUM('draft','on_sale','reserved','sold','off_shelf') | 否 | 'draft' | 状态机 |
| attributes | JSON | 是 | NULL | 类目差异属性，如 `{"interface":"HDMI"}` |
| view_count | INT UNSIGNED | 否 | 0 | 浏览量 |
| published_at | DATETIME(3) | 是 | NULL | 发布时间，草稿为 NULL |
| created_at | DATETIME(3) | 否 | CURRENT_TIMESTAMP(3) | |
| updated_at | DATETIME(3) | 否 | CURRENT_TIMESTAMP(3) | ON UPDATE |

**索引**：`idx_market(status, campus_id, category_id, published_at)` 覆盖集市列表；`idx_seller(seller_id, status)` 供"我的发布"；`idx_mail(support_mail)` 供"只看支持邮寄"。

**约束**：`ck_price_nonneg CHECK (price >= 0)`；三个外键均 `ON DELETE RESTRICT`——有商品引用时不允许删校区/分类/用户。

**设计说明**：
1. 集市列表只查 `status IN ('on_sale','reserved')`，已预订的商品仍要露出（否则买家点进去看到"已下架"会困惑），已售出与已下架不进入列表；
2. `attributes` 用 JSON 而非宽表，是因为教材、显示器、自行车的字段完全不同，建 20 张属性表不现实；本期只做展示，不做属性筛选，将来要筛可加生成列建索引。

### 4.12 trade（交易单）

**用途**：成交记录与并发控制的焦点。一件商品同时只能有一笔"已确认"交易。

| 列名 | 类型 | 可空 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| id | BIGINT UNSIGNED | 否 | 自增 | PK |
| product_id | BIGINT UNSIGNED | 否 | — | FK → product.id |
| buyer_id | BIGINT UNSIGNED | 否 | — | FK → user.id |
| seller_id | BIGINT UNSIGNED | 否 | — | FK → user.id |
| status | ENUM('pending','confirmed','completed','cancelled','rejected','aborted') | 否 | 'confirmed' | 状态机；先到先得，创建即 `confirmed`，`pending`/`rejected` 仅作兼容保留 |
| delivery | ENUM('meetup','mail') | 否 | 'meetup' | 面交 / 邮寄 |
| cancel_reason | VARCHAR(200) | 是 | NULL | 取消或中止原因 |
| created_at | DATETIME(3) | 否 | CURRENT_TIMESTAMP(3) | |
| confirmed_at | DATETIME(3) | 是 | NULL | 确认时间 |
| completed_at | DATETIME(3) | 是 | NULL | 完成时间 |
| confirmed_product_id | BIGINT UNSIGNED | 是 | 生成列 | `IF(status='confirmed', product_id, NULL)` STORED |

**索引**：`uk_confirmed_product(confirmed_product_id)`——**只对已确认交易生效的唯一索引**；`idx_buyer(buyer_id, status)`、`idx_seller(seller_id, status)`。

**约束**：`ck_trade_not_self CHECK (buyer_id <> seller_id)`；三外键 `ON DELETE RESTRICT`（交易凭证不可因删商品而消失）。

**设计说明**（本表是全库最关键的设计）：
1. MySQL 8 没有部分唯一索引，`uk_confirmed_product` 直接建在 `product_id` 上会导致"同一商品的多笔记录"互相冲突，所以引入生成列：只有 `status='confirmed'` 时才等于 `product_id`，其余状态为 `NULL`。MySQL 唯一索引允许多个 `NULL`，于是**同一商品最多一笔 `confirmed`**，其余历史记录（已完成、已取消、已中止）不占位；
2. 本项目采用**先到先得**：买家点「立即购买」，事务里直接 `INSERT ... status='confirmed'`，数据库在插入瞬间就判定唯一性，第二个并发请求立即拿到 1062，不需要"卖家确认"这一步，也不需要先查后改；
3. 交易完成、取消、中止后生成列自动回到 `NULL`，商品位释放，可以再次成交——不需要任何清理任务；
4. 冲突时数据库抛 1062，后端捕获后返回 `409 TRADE_ALREADY_CONFIRMED`，前端提示"该商品已被预订"；
5. `aborted` 与 `cancelled` 分开：前者是账号禁用或管理员中止，后者是双方协商，责任归属不同；`pending`/`rejected` 保留在枚举里仅为兼容旧数据与接口，新流程不再产生这两个值。

| target_id | BIGINT UNSIGNED | 否 | — | 按类型解释为商品/用户/会话 ID |
| conversation_id | BIGINT UNSIGNED | 是 | NULL | 会话类举报必填，用于限定授权范围 |
| type | ENUM('fake_info','prohibited','harassment','fraud','contact_leak','other') | 否 | — | 举报类型 |
| reason | VARCHAR(500) | 否 | — | 举报理由 |
| evidence_urls | JSON | 是 | NULL | 举报人上传的截图地址数组 |
| allow_chat_access | TINYINT(1) | 否 | 0 | 举报人是否同意平台查看相关聊天片段 |

### 4.14 chat_access_grant（聊天片段查看授权）

**用途**：一次授权 = 一个举报单 + 一个会话 + 一个时间窗 + 24 小时有效期。

| 列名 | 类型 | 可空 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| id | BIGINT UNSIGNED | 否 | 自增 | PK |
| report_id | BIGINT UNSIGNED | 否 | — | FK → report.id，级联删除 |
| admin_id | BIGINT UNSIGNED | 否 | — | 授权给谁，FK → user.id |
| conversation_id | BIGINT UNSIGNED | 否 | — | 授权范围：哪个会话 |
| window_start | DATETIME(3) | 否 | — | 时间窗起点，默认举报前 7 天 |
| window_end | DATETIME(3) | 否 | — | 时间窗终点 |
| reason | VARCHAR(200) | 否 | — | 管理员填写的查看理由 |
| status | ENUM('active','expired','revoked') | 否 | 'active' | |
| created_at | DATETIME(3) | 否 | CURRENT_TIMESTAMP(3) | |
| expires_at | DATETIME(3) | 否 | — | 创建后 24 小时 |
| active_report_id | BIGINT UNSIGNED | 是 | 生成列 | `IF(status='active', report_id, NULL)` STORED |

**索引**：`uk_active_grant(active_report_id, admin_id)`——同一举报单、同一管理员**同时最多一条有效授权**；`idx_report(report_id)`。

**约束**：`ck_grant_window CHECK (window_start < window_end)`。

**设计说明**（这是本轮修正的一处设计缺陷）：
1. 早期写法是 `UNIQUE(report_id, admin_id, status)`。它的问题是：管理员第一次申请、授权过期后 `status` 变成 `expired`，再申请一条 `active` 时，唯一索引里已有 `(1, 1, 'active')` 之外的组合，看似没问题；但**同一条记录从 `active` 改成 `expired` 再想改回 `active`**，或者历史里残留过 `active` 记录，就会撞键，表现为"永远无法再次申请"；
2. 改用生成列 `active_report_id`，只让 `status='active'` 的行参与唯一性，`expired`/`revoked` 全部为 `NULL`，彼此不冲突。语义与 `trade.confirmed_product_id` 完全一致，两处用同一套写法，评审时也好解释；
3. 授权到期不是靠定时任务改状态，而是查询时判断 `expires_at > NOW()`；每日清理任务只负责把过期记录置 `expired`，即使任务没跑，`active_report_id` 仍然占用唯一键——所以清理任务必须实现，且要幂等。

## 5 物理设计

### 5.1 存储估算与增长预期

| 表 | 首年预估行数 | 单行估算 | 说明 |
| --- | --- | --- | --- |
| campus | 5～8 | 200 B | 几乎不变 |
| user / user_profile | 500 | 600 B | 校内用户 |
| category | 20 | 100 B | |
| product | 3 000 | 800 B | 含 JSON 属性 |
| product_image | 9 000 | 300 B | 平均 3 张/商品 |
| favorite | 10 000 | 60 B | |
| conversation | 6 000 | 150 B | 每件商品约 2 个咨询 |
| message | 120 000 | 200 B | 单条几十字节，聊天量大 |
| contact_exchange | 800 | 120 B | |
| block | 300 | 60 B | |
| trade | 2 500 | 150 B | |
| report | 200 | 700 B | |
| chat_access_grant | 300 | 250 B | |
| admin_audit_log | 2 000 | 400 B | |

结论：总量在 200 MB 量级，单表最大的是 `message`（约 12 万行、30 MB），远未到需要分表的程度。

### 5.2 两处"部分唯一"的生成列

MySQL 8 没有 PostgreSQL 那样的部分唯一索引（`WHERE status='...'`），本项目用**生成列 + 唯一索引**表达同样的语义，两处写法一致：

| 表 | 生成列 | 表达式 | 唯一索引 | 语义 |
| --- | --- | --- | --- | --- |
| trade | confirmed_product_id | `IF(status='confirmed', product_id, NULL)` | uk_confirmed_product | 一件商品同时最多一笔已确认交易 |
| chat_access_grant | active_report_id | `IF(status='active', report_id, NULL)` | uk_active_grant(active_report_id, admin_id) | 同一举报单 + 同一管理员同时最多一条有效授权 |

为什么可行：唯一索引对 `NULL` 不做去重判断，多行 `NULL` 可以共存；只有满足条件的行才"占位"，条件一变（状态流转）自动让位，不需要触发器也不需要定时清理。

代价与注意：
1. 生成列是 `STORED`，占一点存储，但能建索引；`VIRTUAL` 列在 MySQL 8 也能建索引，这里选 `STORED` 是为了 `EXPLAIN` 更直观；
2. 生成列不能手工赋值，ORM 里必须标记为只读，否则插入时报 `ERROR 3105`；
3. `active_report_id` 依赖"过期即改状态"的清理任务，任务漏跑会导致旧授权一直占位。清理任务按 `expires_at < NOW()` 批量置 `expired`，可重复执行。

### 5.3 是否分区

**不分区**。理由：

- 唯一索引要求分区键必须包含在所有唯一键里，一旦按时间分区，`uk_confirmed_product` 与主键都得带上分区键，语义被破坏；
- 单表最大 30 MB，分区带来的收益远小于维护成本；
- 将来真要归档，按 `created_at` 把两年前的 `message` 迁到历史表即可，不需要分区表。

## 6 安全保密设计

### 6.1 敏感字段与处理方式

| 数据 | 是否收集 | 存储方式 | 对外展示 |
| --- | --- | --- | --- |
| 昵称、头像 | 是 | 明文 | 展示 |
| 校区 | 是 | `campus_id` | 展示（只到校区级） |
| 学号邮箱 | 是 | `user.email` 明文（登录用） | **不展示**，只显示"已认证"徽章 |
| 真实姓名 | **不收集** | — | — |
| 手机号 | 选填 | `user_profile.phone_enc`，AES-256 密文 | 默认打码，双方同意后按会话单独返回 |
| 微信号 / QQ | **不收集** | 聊天中出现即打码，原文不落库 | 同上 |
| 宿舍楼栋 / 精确地址 | **不收集** | — | 面交地点由聊天约定 |
| 精确经纬度 | **不收集** | — | — |

### 6.2 打码规则

1. 手机号：`1[3-9]\d{9}`；微信号：`wxid_[a-zA-Z0-9]+` 或"微信/威信 + 号码"；QQ：`[1-9]\d{4,10}`；
2. 命中即替换为 `[联系方式已隐藏，可申请交换]`，**在服务端写入前完成**，原文既不落库也不推送；
3. 商品标题与描述同样过滤：提交时若命中，返回提示"请勿在描述中填写联系方式"，强制打码后才允许发布；
4. 打码不依赖前端：即使绕过页面直接调接口，写入的也是打码文本。

### 6.3 权限矩阵

| 操作 | 游客 | 登录用户 | 本人（发布者/参与者） | 管理员 | 超级管理员 |
| --- | --- | --- | --- | --- | --- |
| 浏览在售商品 | ✓ | ✓ | ✓ | ✓ | ✓ |
| 查看草稿 | ✗ | ✗ | ✓ | ✗ | ✗ |
| 发布 / 编辑商品 | ✗ | ✓ | ✓ | ✗ | ✗ |
| 发起咨询 | ✗ | ✓ | ✗（不能咨询自己） | ✗ | ✗ |
| 读会话消息 | ✗ | ✗ | ✓（仅参与方） | ✗（默认不可读） | 仅授权窗口内 |
| 交换联系方式 | ✗ | ✓ | ✓ | ✗ | ✗ |
| 接受交易 | ✗ | ✗ | ✓（卖家） | ✗ | ✗ |
| 处理举报 | ✗ | ✗ | ✗ | ✓ | ✓ |
| 批准查看聊天片段 | ✗ | ✗ | ✗ | ✗ | ✓ |
| 禁用账号 / 下架商品 | ✗ | ✗ | ✗ | ✓ | ✓ |

会话读取的校验条件是 `conversation_id + 当前用户 ∈ {buyer_id, seller_id}`，两个条件缺一不可，仅靠"登录了"不够。

### 6.4 审计与日志

- 所有后台动作写 `admin_audit_log`：谁、何时、对什么、做了什么；查看聊天片段额外记录 `message_id` 列表；
- 该表在服务层禁止 UPDATE / DELETE；
- 应用日志里手机号、邮箱只记长度或掩码，聊天内容不写日志；
- 账号注销时删除个人信息（`user` / `user_profile` / `message`），交易凭证去标识化保留（保留订单号、金额、时间，去掉身份关联）。

### 6.5 备份与恢复

课程项目也要能"演示前不怕手滑"：

- 每日 02:00 用 `mysqldump --single-transaction` 全量导出，保留 7 天；`--single-transaction` 保证备份期间不锁表；
- 开启 binlog（`log_bin=ON`），至少保留 7 天，出问题时可按时间点恢复；
- 答辩或验收前手工执行一次 `mysqldump` 并把文件放本地，避免误操作（例如演示并发时插入了脏数据）导致主流程跑不起来；
- 恢复演练至少做一次：在测试库导入备份，确认 `SHOW TABLES` 为 16 行、`campus` 有 5 条记录。

## 7 优化设计

### 7.1 典型查询与执行计划预期

| 查询 | SQL 要点 | 预期使用索引 | 说明 |
| --- | --- | --- | --- |
| 集市列表 | `WHERE status IN ('on_sale','reserved') AND campus_id=? ORDER BY published_at DESC LIMIT 20` | idx_market | 最左列 status 是 `IN`，仍能用到后续列 |
| 不限校区 | 去掉 `campus_id` 条件 | idx_market 部分前缀 | 走 `status` 前缀，扫描量略大但可接受 |
| 只看邮寄 | `AND support_mail=1` | idx_mail 或 idx_market | 校区固定时用 idx_market 更优，由优化器选择 |
| 我的发布 | `WHERE seller_id=? AND status=?` | idx_seller | |
| 聊天记录 | `WHERE conversation_id=? AND id<? ORDER BY id DESC LIMIT 20` | idx_conv_time | 游标翻页，无 OFFSET |
| 待处理举报 | `WHERE status='pending' ORDER BY created_at` | idx_status_time | 后台首页 |

### 7.2 覆盖索引与回表

`idx_market(status, campus_id, category_id, published_at)` 只覆盖"筛选 + 排序"，列表还要取 `title`、`price`、封面图，仍然回表。这是有意的取舍：把 `title`、`price` 也塞进索引会让索引变宽、写入变慢，而列表每页只有 20 行，回表成本可忽略。

聊天记录用 `idx_conv_time(conversation_id, id)` 做主键式游标翻页，深翻页不会退化——这是本项目唯一需要防"翻到第 1000 页"的地方。

### 7.3 N+1 与批量查询

列表接口一次性取齐关联信息，避免逐条查询：

```sql
-- 一次取 20 条商品及其卖家、校区、分类、封面
SELECT p.*, c.name AS campus_name, c.short_name, cat.name AS category_name,
       u.nickname, u.avatar_url, u.status AS seller_status,
       (SELECT url FROM product_image i WHERE i.product_id = p.id ORDER BY i.sort_no LIMIT 1) AS cover_url
FROM product p
JOIN campus c   ON c.id = p.campus_id
JOIN category cat ON cat.id = p.category_id
JOIN user u     ON u.id = p.seller_id
WHERE p.status IN ('on_sale','reserved') AND p.campus_id = ?
ORDER BY p.published_at DESC
LIMIT 20 OFFSET ?;
```

会话列表同理：未读数存在 `conversation` 上，不在列表里 `COUNT(message)`。

### 7.4 慢查询预判与对策

| 风险点 | 现象 | 对策 |
| --- | --- | --- |
| 集市不限校区 + 只按价格排序 | 无法用索引排序，出现 filesort | 数据量小可接受；若变慢，加 `(status, price)` 索引 |
| 消息按会话分页用 OFFSET | 深翻页越来越慢 | 已改为游标 |
| 举报列表按 `handle_note` 模糊查询 | 全表扫描 | 本期不支持按说明搜索，只按状态/类型/时间 |
| 后台统计"某校区商品数" | 每次 COUNT | 演示阶段可接受；将来加统计表或缓存 |
| 生成列未加索引 | 唯一校验变全表扫 | 已建 `uk_*` |

---

### 7.5 事务边界与一致性

所有涉及多表写入的操作都在一个事务里完成，边界如下：

| 操作 | 事务内包含的写入 | 一致性要求 |
| --- | --- | --- |
| 立即购买（抢单） | `trade` 插入 `confirmed`；`product` 置 `reserved` | 两步同事务；插入撞 1062 即回滚，商品状态不前进 |
| 完成交易 | `trade` 置 `completed`；`product` 置 `sold` | |
| 取消交易 | `trade` 置 `cancelled`；`product` 回 `on_sale` | |
| 禁用账号 | `user.status='disabled'`；其 `on_sale` 商品置 `off_shelf`；其 `confirmed` 交易置 `aborted` | 三张表联动，缺一步就会出现"人已禁用、商品仍在卖" |
| 发消息 | `message` 插入；`conversation.last_message_at` 与未读数更新 | 同事务，保证列表排序与红点一致 |
| 举报处置 | `report` 更新；`admin_audit_log` 插入；必要的 `product` / `user` 联动 | 处置必须留痕，两者同事务 |

并发要点：

1. 所有状态流转语句都带前置状态（`WHERE status = '...'`），影响行数为 0 即视为冲突并回滚；
2. 抢单不依赖行锁：唯一索引在 `INSERT` 的那一刻就完成判定，冲突方直接收到 1062，比"先 `SELECT` 再 `UPDATE`"少一次往返、也少一个 TOCTOU 窗口；
3. 唯一索引冲突（1062）统一映射为 `409`，不向用户暴露数据库错误码；
4. 事务隔离级别保持默认 `REPEATABLE READ`，不做全局修改——并发正确性由唯一索引保证，与隔离级别无关；

### 7.6 与本设计相关的已知限制

| 限制 | 影响 | 后续方案 |
| --- | --- | --- |
| `attributes` 不支持按属性筛选 | 用户不能筛"24 寸显示器" | 用生成列 + 索引，或引入 ES |
| 未读数是计数器 | 极端并发下可能偏差 | 定期校准任务；本课程量级不触发 |
| 消息表无冷热分离 | 理论上有增长压力 | 按 `created_at` 归档历史消息 |
| 无分库分表 | 单库单表 | 课程项目规模不需要，贸然引入会破坏唯一索引约束 |
| 生成列占用存储 | 每行多 8 字节 | 可接受，换取数据库层的一致性保证 |

映射要点：

1. **枚举**：`role`、`status` 等用 Python `Enum` 映射 MySQL `ENUM`，值使用小写下划线，与接口输出一致；
2. **金额**：`price` 映射 `Decimal`，禁止 `float`，序列化时量化到 2 位；

### 附录 E　常见问题

**Q1：为什么是 16 张表，不是 17 张？**
概念实体有 14 个（校区、用户、用户资料、分类、商品、图片、收藏、会话、消息、联系方式交换、拉黑、交易、举报、智能体会话），加上两张支撑表（聊天片段授权、审计日志），合计 16 张。早期文档里写"17 张"是重复计入了 `chat_access_grant`，本版已统一为 16，E-R 图、关系模式、本文档三处一致。

**Q2：为什么不用物理外键的级联删除？**
商品、交易、会话都用 `ON DELETE RESTRICT`。删除一件商品会连带删掉它的交易记录，而交易记录是双方履约的凭证，不能因为卖家删商品就消失。只有纯从属对象（`product_image`、`message`）用 `CASCADE`——它们离开父对象没有独立含义。

**Q3：状态为什么用 `ENUM` 而不是 `TINYINT`？**
`ENUM` 把值域写进了表结构，应用层写错状态值会被数据库直接拒绝；`TINYINT` 需要在代码里维护一份映射，两处容易不一致。代价是加状态要改表结构（`ALTER TABLE`），但本项目的状态机在需求阶段已经定死，不存在频繁新增状态的情况。

**Q4：生成列会不会让 ORM 报错？**
会，如果模型里把它当普通列赋值。SQLAlchemy 用 `Computed()` 声明后，`INSERT`/`UPDATE` 不会带上该列，读取时正常返回。这一点已写进附录 B 的第 12、14 行，柯燕纯和廖颖欣对齐字段时需要注意。

**Q5：为什么不把未读数做成视图或统计表？**
视图每次查询都要扫描 `message`，列表页会变成 N+1；统计表需要额外的写入与一致性维护。未读数存在 `conversation` 上，与消息写入同事务更新，实现最简单、读取最快，误差窗口只在极端并发下出现，课程项目量级不会触发。

**Q6：如果将来加一个校区，要改哪些地方？**
只改数据：`INSERT INTO campus (...)`。前端筛选器通过 `GET /api/campuses` 拉取，自动出现新选项；发布表单同理。代码零改动——这正是把校区做成表而不是枚举的原因（AC-17）。
