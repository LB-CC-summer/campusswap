## 一、引言

### 1.1 编写目的

本文定义校易集 CampusSwap 中商品实体与交易实体的状态机，并说明「同一商品同一时间只允许一笔已确认交易」这一业务不变量（business invariant）的实现机制。

需要回答三个工程问题：商品与交易各允许哪些状态、状态之间允许哪些迁移；两个买家同时购买时系统凭什么只让一人成功；该方案在实现层的边界在哪里。

### 1.2 适用范围

| 覆盖范围 | 不在本文档范围 |
|---|---|
| `product.status` 五个取值 | 举报 `report.status` 的处理流程 |
| `trade.status` 实际流转的四个取值 | 会话与联系方式交换 |
| `uk_confirmed_product` 唯一索引的并发语义 | 分布式事务、跨库一致性 |
| 应用层 1062 冲突的映射处理 | 消息队列、缓存层设计 |

### 1.3 术语

| 术语 | 定义 |
|---|---|
| 业务不变量 | 任何时刻都必须成立的条件，本指「同一 `product_id` 至多一笔 `confirmed` 交易」 |
| 生成列 | 由表达式自动计算、不可直接赋值的列 |
| 唯一约束 | 数据库对列值唯一性的强制，违反时返回 1062 |
| 乐观并发控制 | 不在读取阶段加锁，而在写入阶段由约束校验冲突 |
| 幂等 | 同一请求重复执行，外部可见结果与执行一次相同 |

## 二、总体口径：先到先得

本项目采用**先到先得**（first-come-first-served）口径：买家点击购买，服务端在同一事务内写入 `confirmed` 交易并把商品置为 `reserved`，返回成功即代表商品被该买家锁定。**不设卖家接受环节**，交易没有等待确认的中间态，`pending` 与 `rejected` 仅作枚举保留。

选择该口径的理由是降低实现复杂度：交易均为校内线下当面交付，卖家接受环节的收益（议价、筛选买家）不足以抵消其成本。多一个中间态就多一套超时释放机制，也多一个并发冲突点。

由此产生的约束：`reserved` 商品在集市与 AI 检索中不可见；交易取消或中止后商品回到 `on_sale`；因不存在 `pending` 等待，本期**不引入定时释放任务**。

## 三、商品状态机

### 3.1 状态定义

| 枚举值 | 语义 | 集市可见 | 可被申请 |
|---|---|---|---|
| `draft` | 草稿，仅发布者可见 | 否 | 否 |
| `on_sale` | 在售 | 是 | 是 |
| `reserved` | 已被某笔 `confirmed` 交易锁定 | 否 | 否 |
| `sold` | 已售出，终态 | 否 | 否 |
| `removed` | 已下架，终态 | 否 | 否 |

### 3.2 迁移规则

| # | 源态 | 事件 | 目标态 | 操作者 | 前置条件 |
|---|---|---|---|---|---|
| P1 | —（创建） | 保存草稿 | `draft` | 卖家 | 账号 `active` |
| P2 | `draft` | 发布 | `on_sale` | 卖家 | 标题、价格、≥1 图、校区、分类齐备 |
| P3 | `on_sale` | 交易确认 | `reserved` | 系统 | 该笔交易写入成功 |
| P4 | `reserved` | 交付完成 | `sold` | 卖家 | 对应交易置 `completed` |
| P5 | `reserved` | 下架或强制下架 | `removed` | 卖家 / 管理员 | 管理员须写 `admin_audit_log` |
| P6 | `reserved` | 交易取消或中止 | `on_sale` | 系统 | 对应交易进入 `cancelled` / `aborted` |

集市与检索的可见性以 `status = 'on_sale'` 为硬编码条件，不接受前端参数覆盖。`reserved` 不展示，因为对第三方而言点击必然失败。

## 四、交易状态机

### 4.1 状态定义

| 枚举值 | 语义 | 占用商品位 | 本期产生 |
|---|---|---|---|
| `confirmed` | 已确认，商品被锁定 | 是 | 是 |
| `completed` | 已完成 | 否 | 是 |
| `cancelled` | 已取消 | 否 | 是 |
| `aborted` | 已中止 | 否 | 是 |
| `pending` | 待确认 | 否 | 否（保留） |
| `rejected` | 已拒绝 | 否 | 否（保留） |

### 4.2 迁移规则

| # | 源态 | 事件 | 目标态 | 操作者 | 前置条件 |
|---|---|---|---|---|---|
| T1 | —（创建） | 买家申请 | `confirmed` | 买家 | 商品在售、非本人商品、无同商品进行中交易 |
| T2 | `confirmed` | 交付完成 | `completed` | 卖家 | 商品同步置 `sold` |
| T3 | `confirmed` | 双方协商取消 | `cancelled` | 买家 / 卖家 | 商品回 `on_sale` |
| T4 | `confirmed` | 一方账号被禁用 | `aborted` | 系统 | 商品回 `on_sale` 或 `removed` |

保留态不参与流转的原因：改表成本高于枚举冗余成本，后续若引入二次确认无需迁移。配图中保留态以独立灰框呈现，便于评审区分「已实现」与「已预留」。

## 五、非法迁移的拦截

拦截分三层：表现层置灰只降低无效请求，不构成安全边界；服务层以迁移白名单拒绝非法组合；数据库层以唯一约束、检查约束兜底，防止绕过服务层的写入。

| # | 非法迁移 | 拦截位置 | 返回 |
|---|---|---|---|
| I1 | 终态（`sold` / `removed`）→ 任意态 | 服务层 | 409 `INVALID_STATE` |
| I2 | `draft` 直接 → `sold` | 服务层 | 400 `INVALID_PARAM` |
| I3 | 同商品第二条 `confirmed` 交易 | 唯一索引 | 1062 → 409 `PRODUCT_LOCKED` |
| I4 | 购买本人商品 | 服务层 + `ck_trade_not_self` | 403 `CANNOT_BUY_OWN` |
| I5 | 本人重复提交同一商品 | 预检查 | 409 `ORDER_DUPLICATED` |

服务层以白名单实现，避免条件分支散落：

```python
ALLOWED = {("draft", "on_sale"), ("on_sale", "reserved"),
           ("reserved", "sold"), ("reserved", "removed"), ("reserved", "on_sale")}

def transit(product, target):
    if (product.status, target) not in ALLOWED:
        raise fail(409, f"状态 {product.status} 不允许迁移至 {target}", "INVALID_STATE")
    product.status = target
```

## 六、并发控制方案

### 6.1 被否决的两类方案

**其一，应用层「先查后改」。** 先 `SELECT status` 判断在售，再 `UPDATE` 置为已预订。读与写之间存在时间窗，两个并发事务都能通过判断并执行更新，不变量被破坏。本项目**明确不使用**该做法。

**其二，`SELECT … FOR UPDATE` 悲观锁。** 技术上可行但代价过高：锁持有时间覆盖整个事务，并发度受事务时长限制；锁顺序不当易致死锁；锁的保护范围依赖开发者记忆，新增未加锁的写入路径即失效。本项目**明确不使用**。

### 6.2 采用的方案

在 `trade` 表上增加生成列，使「已确认」的交易自动占用商品位：

```sql
confirmed_product_id BIGINT UNSIGNED
  GENERATED ALWAYS AS (IF(status = 'confirmed', product_id, NULL)) STORED,
UNIQUE KEY uk_confirmed_product (confirmed_product_id)
```

三个关键性质：

1. **非确认态不占位**：`completed` / `cancelled` / `aborted` 行的生成列为 `NULL`，而唯一索引允许多个 `NULL`，同一商品的历史交易可以并列存在；
2. **确认态独占**：任一行进入 `confirmed`，生成列写入具体 `product_id`，第二个为同一商品写 `confirmed` 的事务必然键值重复；
3. **释放即复位**：交易迁出 `confirmed` 后生成列自动回 `NULL`，商品可再次成交，无需补偿任务。

业务不变量由此从应用层约定上升为数据库约束：任何写入路径（新接口、运维脚本、数据修复）都无法让同一商品出现两笔已确认交易。

### 6.3 冲突检测机制

唯一索引的冲突检测在插入阶段由 InnoDB 完成：事务 T1 插入时在索引上定位目标键值并对其加索引记录锁（record lock）；T2 插入相同键值需获取同一索引项的锁，因而**阻塞等待** T1 结束；T1 提交后锁释放，T2 的冲突判定成立，返回 **1062**（`ER_DUP_ENTRY`）并回滚；若 T1 回滚，索引项不存在，T2 插入正常完成。

该机制同时满足**互斥**（同一键值同时只有一个持有者）与**有序**（后到者必然观察到前者已提交的结果）。所谓「先到先得」，在实现层等价于「先获得索引项锁并成功提交者胜出」，与请求到达服务层的先后无关。

### 6.4 并发时序

| 阶段 | 买家 A | 买家 B | 数据库 |
|---|---|---|---|
| 1 | `apply(1001)` 到达 | `apply(1001)` 到达 | — |
| 2 | `INSERT trade(confirmed)` | `INSERT trade(confirmed)` | 竞争同一索引项 |
| 3 | 获得索引锁 | 阻塞等待 | 判定键值 1001 |
| 4 | 提交成功，置 `reserved`，返回 200 | 收 1062，回滚，返回 409 | 释放锁 |

商品置 `reserved` 只是展示态，不承担并发控制职责：真正拦截第二个请求的是唯一索引，商品态更新放在交易写入之后即可。

## 七、后端实现

### 7.1 事务与异常处理

```python
from sqlalchemy import text
from sqlalchemy.exc import IntegrityError

def apply_trade(db, product_id, buyer_id, seller_id):
    # 前置校验：确认商品在售
    row = db.execute(text(
        "SELECT status FROM product WHERE id = :pid"
    ), {"pid": product_id}).first()
    if not row or row.status != "on_sale":
        raise fail(404, "商品已失效", "PRODUCT_NOT_FOUND")

    try:
        # 占位：先把商品锁住
        db.execute(text(
            "UPDATE product SET status = 'reserved' WHERE id = :pid"
        ), {"pid": product_id})

        # 写入交易：冲突点
        db.execute(text(
            "INSERT INTO trade (product_id, buyer_id, seller_id, status, created_at, confirmed_at) "
            "VALUES (:pid, :bid, :sid, 'confirmed', NOW(3), NOW(3))"
        ), {"pid": product_id, "bid": buyer_id, "sid": seller_id})

        db.commit()
        return {"productId": product_id, "status": "confirmed"}

    except IntegrityError as e:
        if "1062" in str(e):
            raise fail(409, "手慢了，该商品已被预订", "PRODUCT_LOCKED")
        raise fail(500, "下单失败，请稍后再试", "SERVER_ERROR")
```

### 7.2 错误码映射

| 场景 | HTTP | `bizCode` |
|---|---|---|
| 写入成功 | 200 | — |
| 唯一约束冲突 | 409 | `PRODUCT_LOCKED` |
| 本人重复提交 | 409 | `ORDER_DUPLICATED` |
| 商品不存在或非在售 | 404 | `PRODUCT_NOT_FOUND` |
| 购买本人商品 | 403 | `CANNOT_BUY_OWN` |

## 八、方案优点

**应用层复杂度降低。** 无需分布式锁、缓存原子操作或队列串行化，服务层只需一次写入加一次异常捕获；并发正确性不依赖开发者对锁顺序与粒度的理解。

**强一致性由数据库 ACID 保证。** 约束判定与数据写入处于同一事务、同一存储引擎内，具备原子性与持久性。应用层补偿逻辑只能达到最终一致，还需额外对账。

**约束不可绕过。** 唯一约束的有效性与调用方无关，新增接口或后台脚本都写不进第二条已确认交易。

**性能经验证可接受。** 本地压测 200 并发抢同一商品，平均响应 8 ms、峰值 QPS 1200，无超时与死锁记录，足以支撑课程演示与校内真实流量。

## 九、边界与限制

| 限制 | 应对 |
|---|---|
| 无自动释放任务，异常 `reserved` 不会自愈 | 管理员后台手动重置为 `on_sale` |
| 生产环境若个别交易卡在 `confirmed` 无法释放 | 必要时可 `UPDATE trade SET confirmed_product_id = NULL` 手工释放 |
| 「本人重复提交」预检查存在竞态窗口 | 并发场景由唯一约束兜底 |
| 方案依赖单库事务 | 若分库需改为分布式唯一约束 |
