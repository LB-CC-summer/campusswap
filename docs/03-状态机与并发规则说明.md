# 状态机与并发规则说明

> 文档编号：03 ｜ 版本：v1.1 ｜ 日期：2026-11-21
> 基线：《数据库设计说明》3.2.3 / 3.2.4、《核心接口设计说明书》v1.6
> 对应验收项：AC-10（一件商品同一时间只允许一笔成交）

---

## 一、引言

### 1.1 目的与范围

本文定义商品实体与交易实体的状态机，并说明「同一商品至多存在一笔已确认交易」这一业务不变量（business invariant）的实现机制。范围覆盖 `product.status` 与 `trade.status` 的全部合法迁移、`uk_confirmed_product` 唯一索引的并发语义、以及应用层将 1062 冲突映射为 409 的处理链路；不含举报、会话等其余实体的状态设计。

### 1.2 术语

| 术语 | 定义 |
|---|---|
| 业务不变量 | 任何时刻都必须成立的条件，本文指「同一 `product_id` 至多一笔 `confirmed` 交易」 |
| 生成列 | 由表达式自动计算、不可直接赋值的列，即 `trade.confirmed_product_id` |
| 唯一约束 | 数据库层对列值唯一性的强制，违反时返回错误码 1062 |
| 乐观并发控制 | 不在读取阶段加锁，而在写入阶段由约束校验冲突 |
| 事务边界 | 一组要么全部生效、要么全部撤销的数据库操作的起止范围 |
| 幂等 | 同一请求重复执行，外部可见结果与执行一次相同 |

## 二、总体口径：先到先得

本项目采用**先到先得**（first-come-first-served）口径：买家点击购买，服务端在同一事务内写入 `confirmed` 交易并将商品置为 `reserved`，返回成功即代表商品已被该买家锁定。**不设卖家接受环节**，交易不存在等待确认的中间态；`pending` 与 `rejected` 仅作为枚举保留，本期不产生实际流转。

选择该口径的工程理由：本项目交易均为校内线下当面交付，卖家接受环节的收益（议价、筛选买家）不足以抵消其成本——多一个中间态即多一套超时释放机制与一组并发冲突点。在有限开发周期内，减少状态分支即减少线上故障面。

由此产生的约束：`reserved` 商品在集市列表中以置灰态展示、不可被申请，在 AI 检索结果中不出现；交易 `cancelled` / `aborted` 后商品回到 `on_sale`；因无 `pending` 等待，**不引入定时释放任务**，异常 `reserved` 由管理员后台手动重置。

## 三、商品状态机

| 枚举值 | 语义 | 集市可见 | 可被申请 |
|---|---|---|---|
| `draft` | 草稿，仅发布者可见 | 否 | 否 |
| `on_sale` | 在售 | 是 | 是 |
| `reserved` | 已被某笔 `confirmed` 交易锁定 | 是（置灰） | 否 |
| `sold` | 已售出，终态 | 否 | 否 |
| `removed` | 已下架，终态 | 否 | 否 |

| # | 源态 | 事件 | 目标态 | 操作者 | 前置条件 |
|---|---|---|---|---|---|
| P1 | —（创建） | 保存草稿 | `draft` | 卖家 | 账号 `active` |
| P2 | `draft` | 发布 | `on_sale` | 卖家 | 标题、价格、≥1 图、校区、分类齐备；`price ≥ 0` |
| P3 | `on_sale` | 交易确认 | `reserved` | 系统 | 该笔交易写入未触发 1062 |
| P4 | `reserved` | 交付完成 | `sold` | 卖家（买家确认） | 对应交易置 `completed` |
| P5 | `reserved` | 管理员强制下架 | `removed` | 管理员 | 卖家居于 `reserved` 时不得直接下架，须先取消交易（否则出现「商品已下架、交易仍 `confirmed`」的悬空态）；强制下架须写 `admin_audit_log`，交易置 `aborted` |
| P6 | `reserved` | 交易取消或中止 | `on_sale` | 系统 | 对应交易进入 `cancelled` / `aborted` |

集市列表返回 `on_sale` 与 `reserved` 两类：前者正常展示、可点击购买，后者置灰、购买按钮禁用——已预订商品若从列表里凭空消失，用户会以为商品被删，且原型已展示过置灰卡片（见《01-系统设计说明书》C-08）。智能检索则只返回 `on_sale`，其产品语义是「帮我找能买的」。两处差异是刻意的，不是遗漏。

## 四、交易状态机

| 枚举值 | 语义 | 占用商品位 | 本期产生 |
|---|---|---|---|
| `confirmed` | 已确认，商品被锁定 | 是（写入生成列） | 是 |
| `completed` | 已完成 | 否（生成列回 `NULL`） | 是 |
| `cancelled` | 已取消 | 否 | 是 |
| `aborted` | 已中止（账号禁用等） | 否 | 是 |
| `pending` | 待确认 | 否 | 否（保留） |
| `rejected` | 已拒绝 | 否 | 否（保留） |

| # | 源态 | 事件 | 目标态 | 操作者 | 前置条件 |
|---|---|---|---|---|---|
| T1 | —（创建） | 买家申请 | `confirmed` | 买家 | 商品 `on_sale`；非本人商品；无同商品进行中交易；未触发 1062 |
| T2 | `confirmed` | 交付完成 | `completed` | 卖家（买家确认） | 商品同步置 `sold` |
| T3 | `confirmed` | 协商取消 | `cancelled` | 买家 / 卖家 | 商品回 `on_sale` |
| T4 | `confirmed` | 账号被禁用 / 超期未交接 / 违规判定 | `aborted` | 系统 / 管理员 | 商品回 `on_sale` 或 `removed`；中止需在用户记录留痕，与「取消」区分 |

保留态不参与流转的理由：改表成本高于枚举冗余成本，后续若引入二次确认无需迁移；配图中以独立灰框呈现，便于评审区分「已实现」与「已预留」。

## 五、非法迁移的拦截

拦截分三层：表现层（按钮置灰）只降低无效请求，不构成安全边界；服务层以迁移白名单拒绝非法组合；数据库层以唯一约束、检查约束与枚举类型兜底，防止绕过服务层的写入。

| # | 非法迁移 | 拦截位置 | 返回 |
|---|---|---|---|
| I1 | `sold` / `removed` → 任意态（终态不可逆） | 服务层 | 409 `INVALID_STATE` |
| I2 | `draft` 直接 → `sold` | 服务层 | 400 `INVALID_PARAM` |
| I3 | 同商品第二条 `confirmed` 交易 | 唯一索引 | 1062 → 409 `PRODUCT_LOCKED` |
| I4 | 购买本人发布的商品 | 服务层 + `ck_trade_not_self` | 403 `CANNOT_BUY_OWN` |
| I5 | 本人重复提交同一商品 | 预检查 + 唯一索引 | 409 `ORDER_DUPLICATED` |

服务层用白名单而非条件分支：

```python
ALLOWED = {("draft","on_sale"), ("on_sale","reserved"),
           ("reserved","sold"), ("reserved","removed"), ("reserved","on_sale")}

def transit(product, target):
    if (product.status, target) not in ALLOWED:
        raise fail(409, f"状态 {product.status} 不允许迁移至 {target}", "INVALID_STATE")
    product.status = target
```

## 六、并发控制方案

### 6.1 被明确否决的两类方案

**其一，应用层「先查后改」。** 先 `SELECT status` 判断在售，再 `UPDATE` 置为已预订。读与写之间存在时间窗，两个并发事务都能通过判断并执行更新，不变量被破坏。缺陷不在实现细节，而在校验与生效不在同一原子操作内——本项目明确不使用。

**其二，`SELECT … FOR UPDATE` 悲观锁。** 技术上可行，但代价过高：锁持有时间覆盖整个事务，并发度受事务时长限制；锁顺序不当易致死锁；更关键的是，锁的保护范围依赖开发者记忆，新增一条未加锁的写入路径约束即失效，属于「靠自觉」的约束——本项目明确不使用。

### 6.2 采用的方案：生成列 + 唯一索引

```sql
confirmed_product_id BIGINT UNSIGNED
  GENERATED ALWAYS AS (IF(status = 'confirmed', product_id, NULL)) STORED,
UNIQUE KEY uk_confirmed_product (confirmed_product_id)
```

三个关键性质：

1. **非确认态不占位**：`completed` / `cancelled` / `aborted` 行的生成列为 `NULL`，而唯一索引允许多个 `NULL`，历史交易可并列存在；
2. **确认态独占**：任一行进入 `confirmed`，生成列写入具体 `product_id`，第二个为同一商品写 `confirmed` 的事务必然键值重复；
3. **释放即复位**：交易迁出 `confirmed` 后生成列自动回 `NULL`，商品可再次成交，无需补偿任务。

业务不变量由此从应用层约定上升为数据库约束：任何写入路径（新接口、运维脚本、数据修复）都无法绕过该唯一索引。

### 6.3 冲突检测机制

唯一索引的冲突检测发生在**插入阶段**，由 InnoDB 在索引层完成：

1. 事务 T1 插入时，在 `uk_confirmed_product` 上定位目标键值并加索引记录锁（record lock）；
2. 事务 T2 插入相同键值需获取同一索引项锁，因而**阻塞等待** T1 结束；
3. T1 提交后释放锁，T2 的冲突判定成立，返回 **1062**（`ER_DUP_ENTRY`），事务回滚；
4. 若 T1 回滚，索引项不存在，T2 插入正常完成。

该机制同时满足**互斥**（同一键值同时只有一个持有者）与**有序**（后到者必观察到前者已提交的结果）。「先到先得」在实现层等价于「先获得索引项锁并成功提交者胜出」，与请求到达服务层的先后无关。

### 6.4 并发时序

| 阶段 | 买家 A | 买家 B | 数据库 |
|---|---|---|---|
| 1 | `apply(1001)` 到达 | `apply(1001)` 到达 | — |
| 2 | `INSERT trade(confirmed)` | `INSERT trade(confirmed)` | 竞争同一索引项 |
| 3 | 获得索引锁 | 阻塞等待 | 判定键值 1001 |
| 4 | 提交成功 | — | 释放锁 |
| 5 | 置 `reserved`，返回 200 | 收 1062，回滚，返回 409 | — |

## 七、后端实现

### 7.1 事务与异常处理

```python
from sqlalchemy import text
from sqlalchemy.exc import IntegrityError

def apply_trade(db, product_id, buyer_id, seller_id):
    # 幂等提示：仅用于区分「自己重复提交」与「被他人抢走」，
    # 不承担并发保护职责，真正的闸门是唯一索引
    dup = db.execute(text(
        "SELECT id FROM trade WHERE product_id = :pid AND buyer_id = :bid "
        "AND status IN ('confirmed','completed') LIMIT 1"
    ), {"pid": product_id, "bid": buyer_id}).first()
    if dup:
        raise fail(409, "你已申请过该商品", "ORDER_DUPLICATED")

    try:
        # 1) 写入 confirmed 交易：冲突点，1062 在此抛出
        db.execute(text(
            "INSERT INTO trade (product_id, buyer_id, seller_id, status, created_at, confirmed_at) "
            "VALUES (:pid, :bid, :sid, 'confirmed', NOW(3), NOW(3))"
        ), {"pid": product_id, "bid": buyer_id, "sid": seller_id})

        # 2) 商品置 reserved：展示态，不承担并发控制
        db.execute(text(
            "UPDATE product SET status = 'reserved' WHERE id = :pid AND status = 'on_sale'"
        ), {"pid": product_id})

        db.commit()
        return {"productId": product_id, "status": "confirmed"}

    except IntegrityError as e:
        db.rollback()
        if getattr(getattr(e, "orig", None), "errno", None) == 1062:
            raise fail(409, "手慢了，该商品已被预订", "PRODUCT_LOCKED")
        raise fail(500, "下单失败，请稍后再试", "SERVER_ERROR")
```

实现要点：全程不使用 `FOR UPDATE`，不做「先查后改」的分支；1062 通过 `e.orig.errno` 判定而非异常文本匹配；异常路径必须 `rollback`，否则会话中残留未提交变更会被后续请求复用。

### 7.2 错误码映射

| 场景 | HTTP | `bizCode` |
|---|---|---|
| 写入成功 | 200 | — |
| 唯一索引冲突 1062 | 409 | `PRODUCT_LOCKED` |
| 本人重复提交 | 409 | `ORDER_DUPLICATED` |
| 商品不存在或非在售 | 404 | `PRODUCT_NOT_FOUND` |
| 购买本人商品 | 403 | `CANNOT_BUY_OWN` |

## 八、方案优点

**应用层复杂度降低。** 无需分布式锁、缓存原子操作或队列串行化，服务层只需一次写入加一次异常捕获；并发正确性不依赖开发者对锁顺序与粒度的理解。

**强一致性由数据库 ACID 保证。** 约束判定与数据写入处于同一事务、同一存储引擎内，具备原子性与持久性。应用层补偿逻辑只能达到最终一致，且需额外对账。

**约束不可绕过。** 唯一索引的有效性与调用方无关，新增接口或后台脚本都无法写入第二条 `confirmed` 交易；而「先查后改」与悲观锁的正确性依赖每条写入路径都守规矩。

**天然幂等与自动释放。** 生成列随状态自动计算，迁出 `confirmed` 即回 `NULL`，无需补偿任务；配合 `ORDER_DUPLICATED` 预检查，重复提交不产生重复数据。

**失败快速、可观测、性能可接受。** 冲突在写入瞬间暴露为确定错误码，便于统计抢单失败率；锁粒度局限于单个索引项并随提交释放，不阻塞无关商品。

## 九、边界与限制

| 限制 | 应对 |
|---|---|
| 生成列不可写入，赋值即报错 | 迁移与运维脚本禁止出现该列赋值 |
| 无自动释放任务，异常 `reserved` 不会自愈 | 管理员后台手动重置为 `on_sale` |
| `ORDER_DUPLICATED` 预检查存在竞态窗口 | 并发场景由唯一索引兜底，预检查仅影响提示文案 |
| 方案依赖单库事务 | 若分库需改为分布式唯一约束或业务层协调 |

## 十、与 AC-10 的对应

| AC-10 要素 | 落点 | 验证 |
|---|---|---|
| 唯一性 | `uk_confirmed_product` | `SHOW INDEX FROM trade` |
| 原子性 | 单事务完成写入与置位 | 中途异常时商品仍为 `on_sale` |
| 冲突可观测 | 1062 → 409 `PRODUCT_LOCKED` | 响应含 `bizCode` |
| 数据不脏 | 生成列随状态复位 | 取消后同商品可再成交 |
| 幂等 | `ORDER_DUPLICATED` | 连点两次不产生第二条交易 |

演示：两窗口分别登录买家 A、B，同时点击购买；预期一人 200、其余 409；随后 `SELECT id, status, confirmed_product_id FROM trade WHERE product_id = 1001` 仅一行 `confirmed` 且生成列为 `1001`；将其置 `cancelled` 后可再次成交，验证释放链路。
